# 05 · 新旧模型映射与迁移方案

> **覆盖面**：旧 `server/prisma/schema.prisma` 全部 **33 个 Model**。本文件只描述**映射关系与迁移步骤草案**，不含可执行脚本（脚本在实施阶段单独评审）。
> **前提**：项目未上线、无历史生产数据，采用「**建新表 → 只读搬迁 → 切换读写 → 删旧表**」四段式，而非在线平滑迁移。**迁移全程对旧表只读**，这是本方案的硬约束（回滚安全的基础，见 §8）。
> **统计口径**：本文件**不定义新口径**，一切数字以 `00` §3.1 为准 —— 旧 33 / 目标业务表 50 / 新增 20（拆分派生 10 + 无来源 10）；处置 `沿用14 · 改造8 · 扩展2 · 重命名4 · 重构1 · 拆分2 · 合并1 · 删除1 = 33`。第四批已全文复算，见 **§1.5**。
> **校验分层（第四批硬约束，不得混用）**：
> **A. Migration Process Validation**（§6.1）—— 确认「旧数据是否已正确搬到新表」，**允许**引用旧表 / 旧字段（`SalesPipeline` / `Order` / `Quotation_deprecated` / `type` / `items` / `pipelineId`）；
> **B. Target Schema Validation**（§6.2）—— 确认「新 Schema 建成后目标库自身是否完整、干净、可用」，**禁止**再引用旧表作为验证对象；
> **C. Reconciliation**（§6.3）—— 迁移前后**数量与金额对账** + 差异原因 + 异常数据清单。
> **章节定位（硬约束）**：`00`/`01`/`02`/`03`/`04` 引用本文件 `§1`、`§2.2`、`§3`、`§3.3`、`§4`、`§4.4`、`§5`、`§10`、`§10.1`、`§10.5`、`§12`、`§13`；实施文档引用时**不得改名**。

### 1.4 易错点红线（与 `03` §10 完全对齐）

| # | 红线 | 说明 |
|---|---|---|
| 1 | **不得出现 `Lead.opportunityId`** | Lead ↔ Opportunity 全系统**只有一条**外键：`Opportunity.leadId @unique`。旧 `Lead.pipelineId` 必须**搬迁**到 `Opportunity.leadId`，**不是**改名为 `Lead.opportunityId`（见 §3.3） |
| 2 | **不得出现落库的 `Opportunity.stage`** | `stage` 继续由 `pipelineStage.ts` 派生；终态用 `outcome` / `outcomeAt` / `wonAt` / `lostReason` 落库（ADR-03） |

| 6 | **rename / join table 禁止自动 diff** | 见 §13 |
| 7 | **Target Validation 只指向新表** | §6.2 **禁止**出现 `SalesPipeline` / `Order(type=…)` / `Quotation_deprecated`；引用旧表只允许出现在 §6.1（Migration Process Validation）与 §6.3（Reconciliation） |
| 8 | **禁止 unsafe JSON / DateTime / Enum 直转** | 一律走 §11.2 安全函数（`migration_try_jsonb` / `migration_try_timestamp`）+ §10 两阶段；内联 `::json` / `::jsonb` / `::timestamp` / `CAST(x AS <enum>)` **禁止** |

## 3. `SalesPipeline` 拆分迁移（ADR-01）

### 3.1 前置：先拆出 Customer 与 Lead

`SalesPipeline` 同时承载 `Customer` / `Lead` / `Opportunity` / 订单段四层语义。拆分顺序**必须先客户、再线索、最后商机**：

```
Step 1  为每条 SalesPipeline 确保有 Customer
        若 customerId IS NULL → 用 companyName/contactName/email/phone/country 建 Customer（customerNo 按 CUS 补号）
        再写回 SalesPipeline.customerId（保证 Step 3 的 Opportunity.customerId 非空）

Step 2  SalesPipeline.leadId 非空 或 source 非空 → 生成/复用 Lead
        Lead.leadNo     = 按 LEAD 发号（旧 leadNumber 为空则补号，§5）
        Lead.leadName   = SalesPipeline.title
        Lead.ownerId    = SalesPipeline.assignedTo
        Lead.source     = SalesPipeline.source（XIAOMAN → SYNC）
        Lead.productInterest = SalesPipeline.productInterest
        Lead.remark     = SalesPipeline.leadNotes
        Lead.status     = 若该 pipeline 已有下游单据 → CONVERTED，否则按旧值/默认 NEW
        回填 Lead.pipelineId = SalesPipeline.id（供 §3.3 FK 搬迁与 §3.5 LeadItem 映射使用）

Step 3  剩余字段 → Opportunity（§3.2）
```

> Step 2 结束后，`Lead.pipelineId` 是「旧 FK」，**在 §3.3 完成搬迁前不得删除**。

### 3.2 字段级映射 → `Opportunity`

| 旧字段 | 新字段 | 转换规则 |
|---|---|---|
| `pipelineNumber String? @unique` | `opportunityNo String @unique` | 列改名 + 改必填；NULL/空串按 `OPP` 发号（§5） |

| — | `currency` + `exchangeRate` | **`currency = 'CNY'` 时必须同时写 `exchangeRate = 1`**（`amountCny = amount × exchangeRate`，ADR-18）；旧 `estimatedAmount` 注释即 CNY，故两者成对写入，**不得只写 currency 而留 `exchangeRate` 为 NULL** |
| `estimatedCloseDate String?` | `estimatedCloseDate DateTime?` | `migration_try_timestamp()`（§11.2），非法置 NULL |

| `orderAmount` / `orderDate` / `deliveryDate` / `paymentTerms` / `orderStatus` / `orderNotes` | — | 归 `SalesOrder`（§4.3） |
| `sampleType` / `sampleStatus` / `sampleQuantity` / `sampleNotes` | — | 归 `SampleOrder`（§4.4） |
| `activities` | `OpportunityActivity` | 见 §11.3 |

**`probability` 中文 → `IntentLevel` 映射**（旧字段名误导：它存的是「采购意向」而非数字概率）

### 3.3 `Lead.pipelineId` → `Opportunity.leadId` FK 搬迁（第四批：显式 ID mapping）

**背景**：旧库真实外键在 `Lead.pipelineId @unique → SalesPipeline.id`（`onDelete: SetNull`），而 `SalesPipeline.leadId` 只是普通字段。新模型中唯一合法外键是 `Opportunity.leadId @unique`（nullable，`onDelete: SetNull`）。**不得**把 `Lead.pipelineId` 改名为 `Lead.opportunityId`（`03` §10 #2）。

**为什么必须有 ID mapping 表**：旧库有 **3 处**字段保存的是 `SalesPipeline.id` —— `Lead.pipelineId`、`LeadProduct.leadId`、`Order.pipelineId`。若不做显式映射，只能靠「猜测哪个新表保留了旧 id」来 join；一旦 `Opportunity` 改用新 id，全部关联静默断裂。mapping 表是**唯一可信桥**，且可反复读（幂等）。

**前置约束（三条，缺一不可）**

| # | 约束 | 校验 SQL（期望 0） |
|---|---|---|
| 1 | `Lead.pipelineId` 为 nullable unique → 一个 `SalesPipeline` 最多被 1 条 `Lead` 指向 | `SELECT count(*) FROM (SELECT "pipelineId" FROM "Lead" WHERE "pipelineId" IS NOT NULL GROUP BY 1 HAVING count(*)>1) t;` |
| 2 | 每条 `SalesPipeline` 已产出且仅产出 1 条 `Opportunity`（§3.1/§3.2 完成后） | `SELECT (SELECT count(*) FROM "SalesPipeline") - (SELECT count(*) FROM "Opportunity");` |
| 3 | `LeadItem.leadId` 的**重映射已完成**（§3.5）—— 因为丢掉 `Lead.pipelineId` 后无法再定位 | `SELECT count(*) FROM "LeadItem" i LEFT JOIN "Lead" l ON l.id = i."leadId" WHERE l.id IS NULL;` |

**Step 1｜建立新 Opportunity**：按 §3.1 / §3.2 由 `SalesPipeline` 逐行生成（`Opportunity.id` **沿用** `SalesPipeline.id`，即身份映射）。

**Step 2｜写入旧 ID → 新 ID mapping（表结构见 §11.2）**

```sql
-- migration_id_map 在 Phase 0 建好（§11.2）
INSERT INTO migration_id_map(entity, old_id, new_id)
SELECT 'SalesPipeline→Opportunity', sp.id, o.id
FROM   "SalesPipeline" sp
JOIN   "Opportunity"  o ON o.id = sp.id          -- 身份映射；若改用新 id，须改此 JOIN 条件
ON CONFLICT (entity, old_id) DO NOTHING;
```

**Step 3｜`Lead.pipelineId` → `Opportunity.leadId`（经 mapping 回填，不假设 id 相等）**

```sql
UPDATE "Opportunity" o
SET    "leadId" = l.id
FROM   "Lead" l
JOIN   migration_id_map m
       ON m.entity = 'SalesPipeline→Opportunity' AND m.old_id = l."pipelineId"
WHERE  o.id = m.new_id
  AND  o."leadId" IS NULL;
```

**Step 4｜异常兜底（无匹配 → migration_error，不静默丢弃）**

```sql
INSERT INTO migration_error(entity_type, source_id, error_type, error_message, raw_value)
SELECT 'Lead', l.id, 'UNMAPPED_FK',
       'pipelineId 未匹配到 Opportunity（mapping 缺失，或该 SalesPipeline 未产出 Opportunity）',
       l."pipelineId"
FROM   "Lead" l
LEFT JOIN migration_id_map m
       ON m.entity = 'SalesPipeline→Opportunity' AND m.old_id = l."pipelineId"
WHERE  l."pipelineId" IS NOT NULL AND m.new_id IS NULL;
```

**Step 5｜校验通过后才 DROP；迁移后 `Lead` 不再拥有旧 FK**

```sql
-- 前置约束 1 / 2 / 3 全部为 0 后执行

-- 最终校验：每条非空 leadId 必须指向有效 Lead（期望 0）
SELECT count(*) FROM "Opportunity" o
LEFT JOIN "Lead" l ON l.id = o."leadId"
WHERE o."leadId" IS NOT NULL AND l.id IS NULL;

-- 最后一步：DROP 旧列（必须在 §3.5 完成之后）
ALTER TABLE "Lead" DROP COLUMN "pipelineId";
```

> **顺序要点**：`LeadProduct.leadId` 实际指向 `SalesPipeline`，其重映射依赖 `Lead.pipelineId`。因此 **§3.5 必须在 Step 5 的 `DROP COLUMN` 之前完成**。若先 DROP，`LeadProduct` 将无法定位归属 `Lead`，只能人工补建。
> **执行后状态**：`Lead` 不再拥有 `pipelineId` / `productId` / `quantity`；Lead ↔ Opportunity 全库**只有一条**外键 `Opportunity.leadId`（`03` §10 #2 / §13）。

### 3.4 丢弃字段清单

| 旧字段 | 处理 |
|---|---|
| `companyName` / `contactName` / `email` / `phone` / `country` | 丢弃（以 `Customer` 为准，避免冗余不一致） |
| `orderStatus` | 丢弃（值域注释已失效，实际无业务含义） |
| `lead`（旧命名反向关系） | 丢弃（改为 `Lead.opportunity` 反向 relation） |
| `stage` | 保持派生，不落库（ADR-03） |

### 3.5 `LeadProduct` → `LeadItem`（含外键重映射，第四批修正）

**不能简单 `RENAME`**：旧 `LeadProduct.leadId` 的 FK 指向 `SalesPipeline`（**字段名与对象不符**），必须先把值重映射为 `Lead.id`，**禁止 SQL 强转**。

```sql
-- 1) 表改名 + 主键改名（见 §13.5）
ALTER TABLE "LeadProduct" RENAME TO "LeadItem";
ALTER INDEX "LeadProduct_pkey" RENAME TO "LeadItem_pkey";

-- 2) 旧唯一约束 (leadId, productId) 在新模型不再需要 → 改名后 DROP（不保留）
DROP INDEX IF EXISTS "LeadProduct_leadId_productId_key";

-- 3) 重映射 leadId：SalesPipeline.id → Lead.id（依赖 Lead.pipelineId，须在 §3.3 Step 5 之前）
--    路径：LeadItem.leadId(旧值 = SalesPipeline.id) → Lead.pipelineId 反向定位
UPDATE "LeadItem" i
SET    "leadId" = l.id
FROM   "Lead" l
WHERE  l."pipelineId" = i."leadId";      -- 旧值即 SalesPipeline.id

-- 3b) 重映射失败行 → migration_error（不得静默丢弃，也不得参与后续切换）
INSERT INTO migration_error(entity_type, source_id, error_type, error_message, raw_value)
SELECT 'LeadProduct', i.id, 'UNMAPPED_FK',
       'leadId 无法重映射到 Lead.id（对应 SalesPipeline 未生成 Lead）', i."leadId"
FROM   "LeadItem" i
LEFT JOIN "Lead" l ON l.id = i."leadId"
WHERE  l.id IS NULL;

-- 4) 新增列
ALTER TABLE "LeadItem"
  ADD COLUMN "productName" text,          -- 未建档产品名（从 Product.name 兜底回填）
  ADD COLUMN "sort"        integer NOT NULL DEFAULT 0,
  ADD COLUMN "updatedAt"   timestamp(3) NOT NULL DEFAULT now();

-- 5) 新索引（新模型 @@index([leadId]) / @@index([productId])）
CREATE INDEX "LeadItem_leadId_idx"    ON "LeadItem"("leadId");
CREATE INDEX "LeadItem_productId_idx" ON "LeadItem"("productId");

-- 6) 旧 Lead 的单产品路径（Lead.productId + quantity）补一条 LeadItem
INSERT INTO "LeadItem"(id, "leadId", "productId", quantity, "sort", "createdAt", "updatedAt")
SELECT gen_random_uuid(), l.id, l."productId", COALESCE(l.quantity, 1), 0, l."createdAt", now()
FROM   "Lead" l
WHERE  l."productId" IS NOT NULL
  AND  NOT EXISTS (SELECT 1 FROM "LeadItem" i
                    WHERE i."leadId" = l.id AND i."productId" = l."productId");

-- 7) `productName` 兜底回填
UPDATE "LeadItem" i SET "productName" = p.name
FROM "Product" p WHERE p.id = i."productId" AND i."productName" IS NULL;
UPDATE "LeadItem" SET "productName" = '未命名' WHERE "productName" IS NULL;   -- 目标列非空

-- 8) 校验通过后删除旧单产品列（须在切换前）
DELETE FROM "LeadItem" i USING migration_error e
 WHERE e.entity_type = 'LeadProduct' AND e.source_id = i.id
   AND e.error_type = 'UNMAPPED_FK' AND e.resolved = false;   -- 未决行先移出，人工决策后再补
ALTER TABLE "Lead" DROP COLUMN "productId";
ALTER TABLE "Lead" DROP COLUMN "quantity";
```

> **红线（第四批强调）**：`LeadItem.leadId` 必须指向 **`Lead.id`**，**不得**指向 `SalesPipeline.id`。只做表改名而不重映射，会产生「**全部 LeadItem 挂错线索**」的**静默错误**（§13.5 同款红线）。
> **关于用 `Lead.pipelineId` 而非 `migration_id_map`**：`Lead.pipelineId` 是旧库自带真实 FK，§3.1 Step 2 已为每条 `SalesPipeline` 回填归属 `Lead`，因此它本身就是「`SalesPipeline.id` → `Lead.id`」的现成映射；两种写法等价，**实施时择一并在脚本中统一**（若选 mapping 表，需先写入 `entity = 'SalesPipeline→Lead'` 行）。

### 3.6 `outcome` / 终态物化（Q15）

`opportunity.stage` 不落库，但**终态必须一次性物化**：

```sql
-- 有「已确认」的正式订单 → WON；其余 OPEN（LOST 只能人工标记，迁移不猜）
WITH won AS (
  SELECT DISTINCT so."opportunityId" AS oid
  FROM "SalesOrder" so
  WHERE so.status = 'CONFIRMED'
)
UPDATE "Opportunity" o
SET "outcome"   = CASE WHEN w.oid IS NULL THEN 'OPEN'::"OpportunityOutcome"
                       ELSE 'WON'::"OpportunityOutcome" END,
    "outcomeAt" = CASE WHEN w.oid IS NULL THEN NULL ELSE now() END,
    "wonAt"     = CASE WHEN w.oid IS NULL THEN NULL ELSE now() END,
    "lostReason" = NULL
FROM (SELECT o.id, w.oid FROM "Opportunity" o LEFT JOIN won w ON w.oid = o.id) t
WHERE o.id = t.id;
```

> `outcome = OPEN` 时 `outcomeAt` / `wonAt` / `lostReason` 必须为 NULL；`LOST` 需人工逐条确认 `lostReason`，脚本**不得**自动置 LOST。

## 4. `Order` 拆分迁移（按 `type` 五路分发，ADR-02）

### 4.1 总策略

```
旧 Order 每一行，按 type 判定目标表：
  type = 'QUOTE'      → Quotation    + QuotationItem（并与旧 Quotation 表合并，见 §4.2）
  type = 'SAMPLE'     → SampleOrder  + SampleRound(第 1 轮)
  type = 'ORDER'      → SalesOrder   + SalesOrderItem
  type = 'PRODUCTION' → ProductionOrder + ProductionOrderItem
  type = 'SHIPPED'    → Shipment     + ShipmentItem

items（JSON 字符串）→ 逐项展开为 *Item 行（见 §4.6）
```

> 「拆出 5 类单据 + 5 张明细」是 ADR-02 的落点。旧 `Order.pipelineId`（nullable）在**新模型中一律对应 `opportunityId`（必填）**，因此「无商机的订单」是最大阻断项（见 §7.1 B1）。

### 4.2 Step 1~Step 8：`Order(type='QUOTE')` + 旧 `Quotation` → 新 `Quotation`（第四批定稿）

三件事必须一起做：**编号必填化（含兜底 + 去重）**、**两套报价合并（含去重）**、**`(opportunityId, version)` 唯一 + version 重排**。

**两套来源的字段差异**（决定金额写法）：

| | 旧 `Order(type=QUOTE)` | 旧 `Quotation` 表 |
|---|---|---|
| 编号 | `orderNo String?`（可空） | **无编号列** |
| 金额 | `amountCNY Float?`（**只有本位币**） | `amount Float` + `currency String @default("USD")`（**自由文本，非枚举**） |
| 客户 | `customerId String`（非空） | `customerId String?`（**可空**） |
| 标题 | `title String?`（可空） | `title String`（非空） |
| 版本 | 无 | `version Int` |
| 单产品 | `items` JSON | `productId String?` |

**执行顺序总览（不可调换）**

```
Step 1  旧 Quotation 表 RENAME → Quotation_deprecated（原地保留，只读）
Step 2  创建新的目标 Quotation（V1.0 结构）
Step 3  Order(type='QUOTE')      → Quotation
Step 4  Quotation_deprecated     → Quotation（历史报价，须先过 Step 5-A 过滤）
Step 5  去重：5-A 预判（在 Step 4 之前）/ 5-B 审计落库（在 Step 4 之后）
Step 6  QuotationItem（先父记录，后子记录）
Step 7  数量与金额 reconciliation
Step 8  Quotation_deprecated 生命周期收口
```

#### Step 1｜旧 `Quotation` → `Quotation_deprecated`（原地保留，只读）

```sql
ALTER TABLE "Quotation" RENAME TO "Quotation_deprecated";
-- 迁移期间冻结该表写入（只读），避免边迁边改
```

#### Step 2｜创建新的目标 `Quotation`（V1.0 结构）

```sql
-- 由 Phase 1 的 DDL 创建（Prisma migration 生成 CREATE TABLE "Quotation"），
-- 必须发生在 Step 1 之后：RENAME 先腾出物理表名，DDL 才能建出新表。
-- 此处不重复书写 DDL；只确认执行时点与顺序。
```

#### Step 3｜`Order(type='QUOTE')` → `Quotation`

```sql
-- ① 生成 quotationNo（旧 Order.orderNo 可空且无唯一约束）
--    规则：非空且全局唯一 → 沿用原值；其余（NULL / 空 / 重复）→ QU-<yyyyMMdd>-<序号>
--    禁止 count()+1 / max()+1：改用 row_number() 窗口函数一次性生成候选号
WITH cand AS (
  SELECT o.id,
         'QU-' || to_char(o."createdAt", 'YYYYMMDD') || '-' ||
         lpad(row_number() OVER (PARTITION BY to_char(o."createdAt", 'YYYYMMDD')
                                 ORDER BY o."createdAt", o.id)::text, 4, '0') AS new_no
  FROM "Order" o
  WHERE o.type = 'QUOTE'
)
UPDATE "Order" o
SET    "orderNo" = c.new_no
FROM   cand c
WHERE  o.id = c.id
  AND (o."orderNo" IS NULL OR o."orderNo" = ''
       OR EXISTS (SELECT 1 FROM "Order" o3
                  WHERE o3.type = 'QUOTE' AND o3.id <> o.id AND o3."orderNo" = o."orderNo"));
-- 说明：row_number() 只保证「同一批候选」互不重复；若与「沿用的原值」撞号，
--       由 Step 7 的编号唯一性校验兜底，并按 §5.2 重新发号（re-issue），不得回退到 count()+1。

-- ② 合并 A：Order(type='QUOTE') → Quotation
--    ⚠ 旧 Order 仅有 amountCNY（本位币），无原币金额 → 原币金额无法还原，
--      统一按 totalAmount = totalAmountCny = amountCNY 写入，currency='CNY'、exchangeRate=1。
INSERT INTO "Quotation"(id, "quotationNo", "opportunityId", "customerId", version, title,
                        currency, "exchangeRate", "totalAmount", "totalAmountCny",
                        status, notes, "ownerId", "createdBy", "createdAt", "updatedAt")
SELECT o.id, o."orderNo", o."pipelineId", o."customerId",
       1,                                          -- version 先统一置 1，Step 6 之前重排
       COALESCE(o.title, '报价单'),
       'CNY'::"Currency", 1,                       -- 原币不可还原 → 按 CNY 记账（见上⚠）
       COALESCE(o."amountCNY", 0), COALESCE(o."amountCNY", 0),
       CASE o.status WHEN 'DRAFT' THEN 'DRAFT' WHEN 'SUBMITTED' THEN 'SUBMITTED'
                     WHEN 'APPROVED' THEN 'SENT' WHEN 'REJECTED' THEN 'REJECTED'
                     ELSE 'DRAFT' END,
       o.remark, o."createdBy", o."createdBy", o."createdAt", o."updatedAt"
FROM "Order" o WHERE o.type = 'QUOTE';

-- ③ 无商机（pipelineId 为 NULL）的报价单 → 不得静默写入（opportunityId 目标非空）
INSERT INTO migration_error(entity_type, source_id, error_type, error_message, raw_value)
SELECT 'Order', o.id, 'MISSING_REQUIRED_FK',
       'type=QUOTE 但 pipelineId 为 NULL，无法写入 Quotation.opportunityId',
       o."pipelineId"
FROM   "Order" o
WHERE  o.type = 'QUOTE' AND o."pipelineId" IS NULL;
```

#### Step 5-A｜去重规则（**必须在 Step 4 之前预判并落临时表**）

**去重规则（第四批定案，禁止「两边全 INSERT」）**

| 项 | 规则 |
|---|---|
| **优先级** | **`Order(type='QUOTE')` 优先保留**（它承载审批链，`status` 值域更接近目标）；旧 `Quotation` 行仅在**不重复**时保留 |
| **唯一识别依据** | `(opportunityId, currency, round(totalAmountCny, 2), date(createdAt))` —— 四元组相同即判为「同一份报价的两种存储」 |
| **冲突处理** | 丢弃旧 `Quotation` 侧重复行（**不 INSERT**），把 `old_id → new_id` 写入 `migration_id_map` + `migration_error(type='DUPLICATE_SOURCE')` 备查，`resolved=false` 待人工确认 |
| **不可判定的** | 四元组不完备（如 `customerId`/`amount` 为空导致无法比较）→ **不判重**，全部保留并记 `migration_error`，人工复核 |
| **禁止** | ① 两边全部 INSERT；② 按 `title` 文本判重；③ 直接 `DELETE` 旧表 |

```sql
-- 预判重复的旧 Quotation 行（在 Step 4 之前执行）
CREATE TEMP TABLE _quotation_dup AS
SELECT q.id AS old_id,
       so.id AS keep_new_id
FROM   "Quotation_deprecated" q
JOIN   "Quotation" so                                   -- so = Order(type=QUOTE) 侧已入库
       ON  so."opportunityId" = q."opportunityId"
       AND so.currency        = (CASE WHEN q.currency IN ('CNY','USD','EUR','GBP','JPY')
                                      THEN q.currency::"Currency" ELSE 'CNY'::"Currency" END)
       AND round(so."totalAmountCny", 2) = round(q."amount", 2)      -- 见 Step 4 的金额口径
       AND so."createdAt"::date = q."createdAt"::date
WHERE  so."quotationNo" IS NOT NULL;
```

#### Step 4｜`Quotation_deprecated` → `Quotation`（历史报价）

```sql
-- ④ 合并 B：旧 Quotation → Quotation（保留原 id / version；跳过 Step 5-A 判定的重复行）
--    currency 白名单：旧列为自由文本，必须显式映射，禁止 CAST 直转（§10.2）
--    exchangeRate：CNY → 1；非 CNY → 取当日日汇率（rateToCny）；查不到则 NULL + 异常表（§4.7）
INSERT INTO "Quotation"(id, "quotationNo", "opportunityId", "customerId", version, title,
                        currency, "exchangeRate", "totalAmount", "totalAmountCny", "validUntil",
                        status, notes, "createdAt", "updatedAt")
SELECT q.id,
       'QU-' || to_char(q."createdAt", 'YYYYMMDD') || '-' || lpad(row_number() OVER (
              PARTITION BY to_char(q."createdAt", 'YYYYMMDD')
              ORDER BY q."createdAt", q.id)::text, 4, '0'),
       q."opportunityId",
       COALESCE(q."customerId", op."customerId"),
       q.version, q.title,
       CASE WHEN q.currency IN ('CNY','USD','EUR','GBP','JPY')
            THEN q.currency::"Currency" ELSE 'CNY'::"Currency" END,      -- 未知币种 → CNY + 异常表
       CASE WHEN q.currency = 'CNY' THEN 1
            WHEN er."rateToCny" IS NOT NULL THEN er."rateToCny"
            ELSE NULL END,                                              -- 缺汇率 → NULL，不猜 1:1
       q.amount,
       CASE WHEN q.currency = 'CNY' THEN q.amount
            WHEN er."rateToCny" IS NOT NULL THEN q.amount * er."rateToCny"
            ELSE NULL END,                                              -- 缺汇率 → amountCny = NULL
       q."validUntil",
       CASE WHEN q.status IN ('DRAFT','SUBMITTED','SENT','ACCEPTED','REJECTED','EXPIRED')
            THEN q.status::"QuotationStatus" ELSE 'DRAFT'::"QuotationStatus" END,
       q.notes, q."createdAt", q."updatedAt"
FROM "Quotation_deprecated" q
LEFT JOIN "SalesPipeline" op ON op.id = q."opportunityId"
LEFT JOIN "DailyExchangeRate" er
       ON er."currencyCode" = q.currency                  -- 旧列的原始币种（未知币种自然查不到）
      AND er."date" = q."createdAt"::date                 -- §10.5 后 er.date 已是 date 类型
WHERE q.id NOT IN (SELECT old_id FROM _quotation_dup)
  AND q."opportunityId" IS NOT NULL                       -- 无商机 → 异常表（下方）
  AND COALESCE(q."customerId", op."customerId") IS NOT NULL;  -- 客户不可解析 → 异常表（下方）

-- ④b 被过滤掉的三种行必须可追踪，不得静默丢弃
INSERT INTO migration_error(entity_type, source_id, error_type, error_message, raw_value)
SELECT 'Quotation_deprecated', q.id, e.err,
       e.msg, COALESCE(q.currency, '') || '|' || COALESCE(q."customerId", '') || '|' ||
              COALESCE(q."opportunityId", '')
FROM   "Quotation_deprecated" q
CROSS  JOIN LATERAL (
  SELECT 'MISSING_REQUIRED_FK' AS err, 'opportunityId 为 NULL，无法写入新 Quotation' AS msg
  WHERE q."opportunityId" IS NULL
  UNION ALL
  SELECT 'MISSING_REQUIRED_FK',
         'customerId 与商机客户均为空，新表 customerId 非空'
  WHERE q."opportunityId" IS NOT NULL
    AND COALESCE(q."customerId", (SELECT sp."customerId" FROM "SalesPipeline" sp
                                  WHERE sp.id = q."opportunityId")) IS NULL
) e;

-- ④c 未知币种：显式映射为 CNY，同时记录（禁止 CAST 直转、禁止静默丢弃）
INSERT INTO migration_error(entity_type, source_id, error_type, error_message, raw_value)
SELECT 'Quotation_deprecated', q.id, 'UNMAPPED_ENUM',
       'currency 不在 Currency 枚举白名单内，已保守按 CNY 迁移', q.currency
FROM   "Quotation_deprecated" q
WHERE  q.currency IS NOT NULL AND q.currency NOT IN ('CNY','USD','EUR','GBP','JPY');

-- ④d 非 CNY 且查不到历史汇率 → exchangeRate / totalAmountCny 为 NULL（禁止 1:1 猜测）
INSERT INTO migration_error(entity_type, source_id, error_type, error_message, raw_value)
SELECT 'Quotation_deprecated', q.id, 'MISSING_EXCHANGE_RATE',
       '非 CNY 且当日无汇率，exchangeRate / totalAmountCny 置 NULL，待人工补录', q.currency
FROM   "Quotation_deprecated" q
LEFT JOIN "DailyExchangeRate" er
       ON er."currencyCode" = q.currency AND er."date" = q."createdAt"::date
WHERE  q.currency <> 'CNY' AND er."rateToCny" IS NULL;
```

### 4.3 `type = 'ORDER'` → `SalesOrder` + `SalesOrderItem`

> 与 §4.2 同理：旧 `Order` **只有 `amountCNY`（本位币）**，无原币金额与汇率，故 `totalAmount = totalAmountCny = amountCNY`、`currency='CNY'`、`exchangeRate=1`。

```sql
  SELECT o.id,
         'SO-' || to_char(o."createdAt", 'YYYYMMDD') || '-' ||
         lpad(row_number() OVER (PARTITION BY to_char(o."createdAt", 'YYYYMMDD')
                                 ORDER BY o."createdAt", o.id)::text, 4, '0') AS new_no
  FROM "Order" o
  WHERE o.type = 'ORDER'
)
UPDATE "Order" o
SET    "orderNo" = c.new_no
FROM   cand c
WHERE  o.id = c.id
  AND (o."orderNo" IS NULL OR o."orderNo" = ''
       OR EXISTS (SELECT 1 FROM "Order" o3
                  WHERE o3.type = 'ORDER' AND o3.id <> o.id AND o3."orderNo" = o."orderNo"));

-- ② 主表（String → DateTime 一律走安全函数，禁止 NULLIF(...)::timestamp，见 §11.2）

                     WHEN 'SUBMITTED' THEN 'DRAFT'
                     WHEN 'REJECTED' THEN 'CANCELLED'
                     ELSE 'DRAFT' END,
       migration_try_timestamp(o."orderDate"),            -- 非法日期 → NULL + migration_error
       migration_try_timestamp(o."deliveryDate"),
       o."depositAmount", CASE WHEN o."depositPaid" THEN now() ELSE NULL END,
       o."paymentTerms", 'CNY'::"Currency", 1,
       COALESCE(o."amountCNY", 0), COALESCE(o."amountCNY", 0),

  AND o."pipelineId" IS NOT NULL;                          -- 无商机 → 异常表（③）

-- ③ 无商机订单 → 异常表（opportunityId 目标非空，不得静默丢弃）

       'type=ORDER 但 pipelineId 为 NULL，无法写入 SalesOrder.opportunityId', o."pipelineId"
FROM   "Order" o WHERE o.type = 'ORDER' AND o."pipelineId" IS NULL;

-- ④ 非空但非法的历史日期 → 异常表（与 ② 的 NULL 结果对应，供人工补录）
```

### 4.4 `type = 'SAMPLE'` → `SampleOrder` + `SampleRound`（第四批：显式状态映射）

#### 4.4.1 `SampleOrder.status` 显式映射（**禁止重复分支的 CASE**）

| 优先级 | 旧来源 | 旧值 | 新 `status` |
|---|---|---|---|
| 1 | `Order.status` | `REJECTED` | `REJECTED`（**审批否决优先**，覆盖 `stage`） |
| 2 | `Order.stage`（且 `Order.status = 'APPROVED'`） | `SAMPLE_SENT` | `SAMPLE_SENT` |
| 2 | 同上 | `MOLD` | `MOLDING` |
| 2 | 同上 | `DESIGN` | `DESIGNING` |
| 3 | 其余（`DRAFT` / `SUBMITTED` / NULL / 未知 `stage`） | — | `DRAFT`（**保守默认**） |

> **红线**：**禁止** `CASE WHEN xxx THEN 'PENDING' ELSE 'PENDING' END` 这类「两个分支产生同一结果却假装完成映射」的写法。上表每个分支必须产生**不同结果**或**明确兜底**，且所有「被兜底」的行必须同步写入 `migration_error`。

#### 4.4.2 `SampleRound.result` 映射

| 情况 | 处理 |
|---|---|
| 旧库**没有可靠**的轮次结果来源（**当前事实**：`Order` 无轮次结果字段） | 统一 `PENDING`，并明确标注：**「这是 V1.0 历史迁移的保守默认值，不代表业务事实」** |
| 若实施前审计发现旧字段**可区分**状态（如 `SalesPipeline.sampleStatus` 形成封闭值域） | **必须**建立完整「旧状态 → 新状态」映射表，禁止沿用统一 `PENDING` |
| 禁止 | `CASE` 两分支同值；未审计直接猜 `PASS` / `FAIL` |

```sql
-- Phase 0 审计：决定是否需要完整映射（结果封闭且语义清楚 → 建映射表）
SELECT COALESCE("sampleStatus", '<NULL>') AS v, count(*) AS n
FROM   "SalesPipeline" GROUP BY 1 ORDER BY n DESC;

-- 若无封闭值域 → 统一 PENDING（保守默认），并把非空但无法判定的行记录在案
INSERT INTO migration_error(entity_type, source_id, error_type, error_message, raw_value)
SELECT 'SalesPipeline', sp.id, 'UNMAPPED_ENUM',
       'sampleStatus 无可靠映射，SampleRound.result 统一取保守默认 PENDING', sp."sampleStatus"
FROM   "SalesPipeline" sp
WHERE  COALESCE(sp."sampleStatus", '') <> '';
```

**`SampleRoundResult` 允许取值**：`PENDING`（保守默认）、`PASS`、`FAIL`、`CANCELLED`。旧库无来源时，除 `PENDING` 外**一律不得猜测**。

#### 4.4.3 主单与轮次迁移 SQL

```sql
-- 主单（⚠ SampleOrder 表**不得包含** salesOrderId 列）
--   productName 为必填快照：items[0].name → Product.name → '未命名'
--   JSON 一律走 migration_try_jsonb（禁止 o.items::jsonb 直接强转，见 §11.2）
INSERT INTO "SampleOrder"(id, "sampleNo", "opportunityId", "customerId",
                          "productId", "productName", spec, quantity,
                          "sampleType", status, "currentRound",
                          "createdBy", "createdAt", "updatedAt")
SELECT o.id,
       o."orderNo",                                  -- 先沿用，再由 §5 的 SMP 规则统一补号/规范
       o."pipelineId", o."customerId",
       COALESCE(CASE WHEN o."targetType" = 'PRODUCT' THEN o."targetId" END,
                migration_try_jsonb(o.items) -> 0 ->> 'productId'),
       COALESCE(migration_try_jsonb(o.items) -> 0 ->> 'name', p.name, '未命名'),
       migration_try_jsonb(o.items) -> 0 ->> 'spec',
       COALESCE((SELECT sum((i ->> 'quantity')::int)
                 FROM jsonb_array_elements(migration_try_jsonb(o.items)) i), 1),
       NULL,                                          -- sampleType 旧库无对应字段
       CASE                                            -- 显式映射（§4.4.1），无重复分支
         WHEN o.status = 'REJECTED'                      THEN 'REJECTED'
         WHEN o.status = 'APPROVED' AND o.stage = 'SAMPLE_SENT' THEN 'SAMPLE_SENT'
         WHEN o.status = 'APPROVED' AND o.stage = 'MOLD'        THEN 'MOLDING'
         WHEN o.status = 'APPROVED' AND o.stage = 'DESIGN'      THEN 'DESIGNING'
         ELSE 'DRAFT'                                  -- 保守默认
       END::"SampleStatus",
       1, o."createdBy", o."createdAt", o."updatedAt"
FROM "Order" o
LEFT JOIN "Product" p
       ON p.id = COALESCE(CASE WHEN o."targetType" = 'PRODUCT' THEN o."targetId" END,
                          migration_try_jsonb(o.items) -> 0 ->> 'productId')
WHERE o.type = 'SAMPLE'
  AND o."pipelineId" IS NOT NULL;

-- 主单：无商机 → 异常表（opportunityId 目标非空）
INSERT INTO migration_error(entity_type, source_id, error_type, error_message, raw_value)
SELECT 'Order', o.id, 'MISSING_REQUIRED_FK',
       'type=SAMPLE 但 pipelineId 为 NULL，无法写入 SampleOrder.opportunityId', o."pipelineId"
FROM   "Order" o WHERE o.type = 'SAMPLE' AND o."pipelineId" IS NULL;

-- 主单：非法 JSON → 异常表（productName 仍有兜底，不阻断整批）
INSERT INTO migration_error(entity_type, source_id, error_type, error_message, raw_value)
SELECT 'Order', o.id, 'INVALID_JSON',
       'items 非合法 JSON 数组，快照字段已兜底（name→Product.name→未命名），quantity 取 1',
       left(COALESCE(o.items, '<NULL>'), 200)
FROM   "Order" o
WHERE  o.type = 'SAMPLE' AND migration_try_jsonb(o.items) IS NULL
  AND  COALESCE(o.items, '') <> '';

-- 第 1 轮 SampleRound：时间戳一律走安全函数（禁止 NULLIF(...)::timestamp）
INSERT INTO "SampleRound"(id, "sampleOrderId", "roundNo", "designAt", "moldAt", "sentAt",
                          result, "createdBy", "createdAt", "updatedAt")
SELECT gen_random_uuid(), o.id, 1,
       migration_try_timestamp(o."designDate"),
       migration_try_timestamp(o."moldDate"),
       migration_try_timestamp(o."sampleSentDate"),
       'PENDING'::"SampleRoundResult",                -- §4.4.2 保守默认（已记 migration_error）
       o."createdBy", o."createdAt", o."updatedAt"
FROM "Order" o
WHERE o.type = 'SAMPLE'
  AND EXISTS (SELECT 1 FROM "SampleOrder" s WHERE s.id = o.id);   -- 父记录必须已存在

-- 第 1 轮：非法日期 → 异常表
INSERT INTO migration_error(entity_type, source_id, error_type, error_message, raw_value)
SELECT 'Order', o.id, 'INVALID_DATETIME',
       'designDate/moldDate/sampleSentDate 存在非法值，已置 NULL', 
       COALESCE(o."designDate",'') || '|' || COALESCE(o."moldDate",'') || '|' ||
       COALESCE(o."sampleSentDate",'')
FROM   "Order" o
WHERE  o.type = 'SAMPLE'
  AND ((COALESCE(o."designDate",'') <> ''      AND migration_try_timestamp(o."designDate") IS NULL)
    OR (COALESCE(o."moldDate",'') <> ''        AND migration_try_timestamp(o."moldDate") IS NULL)
    OR (COALESCE(o."sampleSentDate",'') <> ''  AND migration_try_timestamp(o."sampleSentDate") IS NULL));
```

> `Order.stage` 的 3 个值只表示「当前处于哪一步」，无法还原「已完成的步骤」。`SampleRound` 的时间戳按非空字段回填，**已越过但旧字段为空的步骤无法还原**（数据缺失，非脚本缺陷），建议迁移后由业务对进行中的打样单做一次人工补录。
> `SampleOrder.feeAmount` / `feeCurrency` / `targetPrice` / `customerSnapshot` 旧库无来源，置 NULL / 默认值。

**补充：`SalesPipeline` 的样品字段**（`sampleType` / `sampleStatus` / `sampleQuantity` / `sampleNotes`）

旧 `SalesPipeline` 还冗余保存了一份样品信息。对**没有** `Order(type=SAMPLE)` 行、但 `sampleQuantity` 非空（或 `sampleNotes` 非空）的商机，须补建一张 `SampleOrder`，否则这部分数据会丢失：

```sql
INSERT INTO "SampleOrder"(id, "sampleNo", "opportunityId", "customerId", "productId",

                          notes, "createdAt", "updatedAt")

       'SM-' || to_char(p."createdAt", 'YYYYMMDD') || '-' || lpad(row_number() OVER (
              PARTITION BY to_char(p."createdAt", 'YYYYMMDD')
              ORDER BY p."createdAt", p.id)::text, 4, '0'),
       p.id, p."customerId", p."productId",
       COALESCE(pr.name, p."productInterest", '未命名'),
       COALESCE(p."sampleQuantity", 1),
       p."sampleType",
       'DRAFT'::"SampleStatus",    -- sampleStatus 旧文案不可信 → 保守默认（§4.4.1 优先级 3）
       1, p."sampleNotes", p."createdAt", p."updatedAt"

LEFT JOIN "Product" pr ON pr.id = p."productId"
WHERE (p."sampleQuantity" IS NOT NULL OR COALESCE(p."sampleNotes", '') <> '')
  AND NOT EXISTS (SELECT 1 FROM "SampleOrder" s WHERE s."opportunityId" = p.id);
```

**`SampleOrder.salesOrderId` 的 DROP 与反向回填（第四批修正为 1 : N，`04` §2 Q10 / §12 #12）**

新模型来源关系**单向**：`SalesOrder.sampleOrderId?`（**非 `@unique`**，`SampleOrder` **1 : N** `SalesOrder`，`onDelete: SetNull`）。因此**不再需要**「最早一一配对」的去重逻辑：

```sql
-- ① 反向回填 SalesOrder.sampleOrderId（1:N —— 同一张 SampleOrder 可被多张 SalesOrder 引用）
--    取该商机下「最早的 SampleOrder」作为来源打样单；无需去重、无需 @unique 配对约束
UPDATE "SalesOrder" so
SET    "sampleOrderId" = COALESCE(
         so."sampleOrderId",
         (SELECT s.id FROM "SampleOrder" s
          WHERE s."opportunityId" = so."opportunityId"
          ORDER BY s."createdAt", s.id LIMIT 1)
       )
WHERE EXISTS (SELECT 1 FROM "SampleOrder" s WHERE s."opportunityId" = so."opportunityId");

-- ② 回填完成后，DROP 残留的旧列（draft1 曾建过 SampleOrder.salesOrderId）
--    必须先执行 ①，否则 ② 之后无法再恢复关联
ALTER TABLE "SampleOrder" DROP COLUMN IF EXISTS "salesOrderId";

-- ③ 校验
--    a) 不得存在「有 sampleOrderId 但指向不存在样单」的订单（期望 0）
SELECT count(*) FROM "SalesOrder" so
LEFT JOIN "SampleOrder" s ON s.id = so."sampleOrderId"
WHERE so."sampleOrderId" IS NOT NULL AND s.id IS NULL;

--    b) 允许一张样单对应多张订单（1:N 的正常形态），只做数量展示，不做断言
SELECT s.id, count(so.id) AS linked_orders
FROM "SampleOrder" s LEFT JOIN "SalesOrder" so ON so."sampleOrderId" = s.id
GROUP BY s.id HAVING count(so.id) > 1 ORDER BY 2 DESC;    -- 允许 > 0 行（这是 1:N 的证据）
```

> **与 `00` / `05` 旧口径的差异（第四批已同步本文件）**：draft2 曾写作「`SalesOrder.sampleOrderId? @unique`，一张打样单最多转 1 张订单」。第三批按业务要求改为 **1 : N**（一次打样 → 客户后续多次下单），故**不再有 `@unique`**，回填逻辑也随之简化。`SampleOrder` 侧只保留 `salesOrders[]` 反向 relation。

### 4.5 `type = 'PRODUCTION'` / `'SHIPPED'`（第四批：显式状态映射 + 运费来源）

**`ProductionOrder.status` 显式映射**（**旧库无细分态，唯一可用值是保守终态**）

| 旧来源 | 旧值 | 新 `status` | 说明 |
|---|---|---|---|
| `Order.status` | `REJECTED` | `CANCELLED` | 审批否决优先 |
| `Order.stage` / 无其他信息 | 任意 | `COMPLETED` | **保守默认**（历史单据视为已完结），必须记 `migration_error` 待业务确认 |

**`Shipment.status` 显式映射**

|---|---|---|
| `Order.shippedDate` | 非空且合法 | `SHIPPED` |
| `Order.shippedDate` | NULL / 空 / 非法 | `DRAFT` |
| `Order.status` | `REJECTED` | `CANCELLED`（优先） |

```sql
INSERT INTO "ProductionOrder"(id, "productionNo", "salesOrderId", status,
```

### 4.5.1 `PurchaseOrderItem.productionOrderItemId` 成本追溯（保留，不删除）

`PurchaseOrderItem.productionOrderItemId?` 是「**生产任务 → 采购 → 实际采购成本**」的追溯基础（`04` §7）：

| 项 | 结论 |
|---|---|
| 是否保留该列 | **保留**。V1.0 不要求完整 MRP，但必须保留成本追溯基础 |
| 迁移来源 | 旧库**无来源** → 一律 `NULL`（不得臆造关联） |
| 新业务 | 由采购单创建流程在「为某生产任务采购」时填写 |
| 追溯口径 | `ProductionOrderItem → PurchaseOrderItem(productionOrderItemId)` 汇总实际采购成本 |

> **红线**：不得以「V1.0 不做 MRP」为由删除该列。删除后成本只能按订单粗估，`Profit.costSnapshot` 的「实际采购成本」将永久失去锚点。

---

**关联重建规则**（`PRODUCTION` / `SHIPPED` 旧行只有 `pipelineId`，**没有 `orderId`**）：

```
salesOrderId = (SELECT so.id FROM "SalesOrder" so
                 WHERE so."opportunityId" = o."pipelineId"
                 ORDER BY so."createdAt", so.id LIMIT 1)
```

若该商机下**不存在** `SalesOrder`（`type=PRODUCTION` 可能先于 `type=ORDER` 创建），脚本须**先补建**一张 `SalesOrder(status=CONFIRMED, 从 pipeline 取金额/日期)` 再挂载 —— 这是第二个阻断项（B2，§7.1）。`JOIN LATERAL` 会**自动跳过**无匹配的行，因此这些行不会静默产生孤儿单据；执行后须核对：

```sql
SELECT (SELECT count(*) FROM "Order" WHERE type = 'PRODUCTION')
     - (SELECT count(*) FROM "ProductionOrder") AS production_gap;   -- 期望 0
SELECT (SELECT count(*) FROM "Order" WHERE type = 'SHIPPED')
     - (SELECT count(*) FROM "Shipment") AS shipped_gap;             -- 期望 0
```

### 4.6 `items` JSON 展开（4 张 `*Item` 表）

旧 `Order.items` 形态（审计确认）：

```json
[{"productId":"...","name":"搪胶鸭子","spec":"12cm","quantity":1000,
  "unitPrice":0.85,"amount":850,"pipelineId":"..."}]
```

> `Order.items` 只流向 **4 张明细表**（`QuotationItem` / `SalesOrderItem` / `ProductionOrderItem` / `ShipmentItem`）；`SampleOrder` **无明细表**（`productName` + `quantity` 单行承载）；`PurchaseOrderItem` 与 `Order.items` **无关**（来源是 `PurchaseOrder`，不参与本步）。

**通用键映射**

| JSON key | 处理 |
|---|---|
| `productId` | → `productId`；在 `Product` 中不存在则置 NULL + 记日志 |
| `name` | → `productName`（**快照，非空**；为空则用 `Product.name` 兜底，再兜底 `'未命名'`） |
| `spec` | → `spec` |
| `quantity` | → `quantity`（各自类型见下） |
| `unitPrice` | → `unitPrice`（`Decimal(18,6)`） |
| `amount` | → `amount`；缺失则算 `quantity × unitPrice` |
| `pipelineId` | **丢弃**（行级归属由父单决定） |
| 数组下标 | → 序号列（各自名称见下） |

**各表列差异（必须分表写 SQL，不可一套通用脚本）**

| 目标表 | 序号列 | 金额列 | 特有约束 |
|---|---|---|---|
| `QuotationItem` | `sort`（**不是 `lineNo`**） | `unitPrice` / `amount` ✓ | `productName` 非空 |
| `SalesOrderItem` | `lineNo` | `unitPrice` / `amount` ✓ | `productName` 非空；`quantity` 为 `Decimal(18,4)` |
| `ProductionOrderItem` | `sort` | **无金额列** | `productName` 非空；`salesOrderItemId?` 可空 |
| `ShipmentItem` | **无序号列** | **无金额列** | `salesOrderItemId` **必填** → 无法匹配订单行时记 `migration_error`（阻断项 B7） |

> `ShipmentItem` 还含 `packageCount` / `grossWeight` / `volume`（旧库无来源，置 NULL）。`ProductionOrderItem` 的 `completedQty` / `defectQty` 置 0，`status` 用默认 `PENDING`。

**安全 JSON 迁移策略（第四批：禁止 unsafe cast）**

`items` 是 `String?`，可能为 `NULL` / `''` / 非法 JSON / 非数组 JSON。**禁止** `json_array_length(o.items::json)` / `o.items::jsonb -> 0` 这类无校验直转 —— 一条坏数据即可让**整批迁移不可控失败**。

```
Step 1  先分类识别：NULL / 空字符串 / 非法 JSON / 合法 JSON（只统计，不改数据）
Step 2  仅「合法 JSON」进入 JSON 转换
Step 3  非法数据写入 migration_error（迁移异常表）
Step 4  不因一条坏数据中断整批
```

```sql
-- Step 1：分类清点（Phase 0 审计）
SELECT CASE
         WHEN items IS NULL                                        THEN 'NULL'
         WHEN items = ''                                           THEN 'EMPTY_STRING'
         WHEN migration_try_jsonb(items) IS NULL                    THEN 'ILLEGAL_JSON'
         WHEN jsonb_typeof(migration_try_jsonb(items)) <> 'array'   THEN 'NOT_ARRAY'
         ELSE 'OK'
       END AS kind, count(*)
FROM "Order" GROUP BY 1 ORDER BY 2 DESC;

-- Step 3：异常行入表（Step 2 只处理 OK / NOT_ARRAY）
INSERT INTO migration_error(entity_type, source_id, error_type, error_message, raw_value)
SELECT 'Order', o.id,
       CASE WHEN o.items = '' THEN 'EMPTY_JSON' ELSE 'INVALID_JSON' END,
       'Order.items 无法解析为 JSON 数组，明细无法展开，待人工补录',
       left(COALESCE(o.items, '<NULL>'), 500)
FROM   "Order" o
WHERE  o.items IS NOT NULL AND o.items <> ''
  AND  (migration_try_jsonb(o.items) IS NULL
        OR jsonb_typeof(migration_try_jsonb(o.items)) <> 'array');
-- 合法 JSON 对象（非数组）→ 记 'NOT_ARRAY'，用 jsonb_build_array(...) 包装后按单行展开
```

| `errorType` | 触发条件 | 迁移动作 |
|---|---|---|
| `NULL_JSON` | `items IS NULL` | **不记异常**（正常：无明细单据），父单正常迁移 |
| `EMPTY_JSON` | `items = ''` | 记异常；父单正常迁移，无明细行 |
| `INVALID_JSON` | 无法解析为 JSON | 记异常；父单正常迁移，明细缺失待补录 |
| `NOT_ARRAY` | 合法 JSON 但非数组 | 记异常；`jsonb_build_array` 包装后展开 |

> **关键约束**：以上四种情况**均不得阻断父单迁移**，也**不得**因明细缺失回滚整批。展开脚本统一使用 §11.2 的 `migration_try_jsonb()`。

### 4.7 币种与汇率口径（`P1-7`，第四批：**历史迁移规则 / 新业务规则严格分开**）

**旧数据币种来源**

| 来源 | 旧默认币种 | 迁移处理 |
|---|---|---|
| `Order.currency` | `CNY`（`default("CNY")`，但为 `String?`） | 白名单映射（§10.2）；非白名单 → `CNY` + 异常表 |
| `Quotation.currency` | `USD`（`default("USD")`，**自由文本**） | 白名单映射；非白名单 → `CNY` + 异常表 |
| `PaymentRecord` | 无币种字段（隐含 CNY） | `CNY` + `exchangeRate = 1` |
| `ProfitRecord.currency` | `CNY` | `CNY` + `exchangeRate = 1`（见 §12.2） |

**统一公式**（ADR-06 / ADR-18）：`amountCny = amount × exchangeRate`，`exchangeRate` 语义 = **1 原币 = x CNY**（即 `rateToCny`）。**禁止**出现 `/ rateToCny` 或任何 `ratePerCNY` 残留（§10.5）。

#### 4.7.1 历史迁移规则（**唯一口径，覆盖此前相互矛盾的两种写法**）

| 历史情形 | `exchangeRate` | `amountCny` | 附加动作 |
|---|---|---|---|
| 币种 = `CNY` | `1` | `= amount` | — |
| 币种 ≠ `CNY`，**当日存在** `DailyExchangeRate.rateToCny` | 该汇率**快照** | `amount × exchangeRate` | — |
| 币种 ≠ `CNY`，**当日无汇率** | **`NULL`** | **`NULL`** | 记 `migration_error(type='MISSING_EXCHANGE_RATE')`，进入历史异常清单 |

> **明确废止的旧写法**：「汇率缺失时 `amountCny = amount`」。该写法等价于假设 **1 外币 = 1 人民币**，会把美元报价按人民币数值入账，属严重数据失真，**禁止**。
> **汇总口径**：`amountCny IS NULL` 的行**不计入** CNY 总额，但必须在 reconciliation 中**单独列示**（§6.3），不得静默丢弃。

#### 4.7.2 新业务规则（与历史迁移规则**严格分开**）

| 新业务情形 | 规则 |
|---|---|
| `currency = 'CNY'` | `exchangeRate = 1`，`amountCny = amount` |
| `currency ≠ 'CNY'` 且**已有有效** `rateToCny` | 允许落库，`amountCny = amount × exchangeRate` |
| `currency ≠ 'CNY'` 且**无有效** `rateToCny` | **禁止确认**任何需要 CNY 金额的业务单据（报价确认 / 订单确认 / 出货确认 / 收付款 / 利润）—— **应用层硬校验**，不是「记日志后继续」 |

> **两者不得混用**：历史迁移允许「先置 `NULL`、后人工补录」（历史数据不可重来）；新业务**不允许**产生 `amountCny IS NULL` 的已确认单据。`04` 的校验与应用层规则以本节为准。

## 5. 编号补号（15 个 code）

旧数据大量编号字段为 `NULL` 或**无 `@unique`**（例外：`pipelineNumber` / `purchaseNo` 有唯一约束，但仍可空）。迁移统一按 `NumberSequence` 发号。

### 5.0 红线：禁止 `count()+1` / `max()+1`

> **`NumberSequence` 的业务编号绝不允许通过 `count()+1` 或 `max()+1` 生成。** 两个致命缺陷：
> ① **并发不安全**：两个事务同时 `max()+1` 会得到同一个号（`SO20270001` / `SO20270001`）；
> ② **历史数据下结果错误**：历史号不连续 / 有洞时，`max()+1` 与筛选条件错配（本文件 §4.2 / §4.3 已因此改为 `row_number()`）。
>
> **唯一合法实现**：`事务` + `行级锁 / 原子 UPDATE` + `编号列唯一约束`（`01` §5.1）。三者缺一不可。

```sql
-- 唯一合法的发号原语（SQL-03 行锁循环的原子步），必须在事务内执行
BEGIN;
  UPDATE "NumberSequence"
     SET "currentValue" = "currentValue" + 1,
         version        = version + 1
   WHERE code = 'SO'
  RETURNING "currentPeriod", "currentValue";      -- 行级锁 + 原子自增 → 天然并发安全
COMMIT;
-- 应用层：拿到 (period, value) 后拼号并写入业务表；业务表编号列必须有 @unique 兜底
```

### 5.1 迁移执行步骤（回填 → 检测重复 → 重新发号 → 同步）

```
Step 1  回填：统计每个业务表缺失 / 重复编号行数
        SELECT count(*) FROM "<T>" WHERE "<COL>" IS NULL OR "<COL>" = '';
Step 2  初始化 NumberSequence：为 15 个 code 各插一行（currentPeriod=''，currentValue=0）
Step 3  按 createdAt 升序逐行发号（编号与时间顺序一致），同一 code 串行（§01 §5.1 行锁算法）
        ⚠ 每张表的编号列必须有 @unique；冲突时重试，不得回退 count()+1
Step 4  重复编号检测 → 异常表（见 §5.2 动作 2）
Step 5  补号完成后，同步 currentPeriod / currentValue 为「历史最大值之后」（模板见下）
Step 6  为补上的编号写 OperationLog(action='DATA_MIGRATION')，便于追溯
```

### 5.2 历史编号的 4 个必经动作（覆盖全部 15 个 `String @unique` 业务编号）

目标 Schema 中 15 个业务编号列为 `String @unique`（回填后必填）。旧库大量为 `NULL` 或重复，因此**逐项**必须完成：

| # | 动作 | 做法 |
|---|---|---|
| 1 | **历史数据回填编号** | 按 §5.1 Step 3 生成 |
| 2 | **发现重复编号 → 异常表** | `migration_error(errorType='DUPLICATE_NUMBER')`，见下方 SQL |
| 3 | **为冲突行重新生成唯一编号** | 用与 Step 3 **相同的规则**重发（**不得** `count()+1`） |
| 4 | **同步 `NumberSequence`** | 把 `currentPeriod` / `currentValue` 推至**历史最大序号之后**（模板见下） |

```sql
-- 动作 2：重复编号检测（对 15 个 code 的业务表逐一执行，替换 <TABLE> / <COL>）
INSERT INTO migration_error(entity_type, source_id, error_type, error_message, raw_value)
SELECT '<TABLE>', t.id, 'DUPLICATE_NUMBER',
       '编号 ' || t."<COL>" || ' 在 <TABLE>.<COL> 上重复，已重新发号', t."<COL>"
FROM   "<TABLE>" t
JOIN  (SELECT "<COL>" FROM "<TABLE>" WHERE "<COL>" IS NOT NULL
       GROUP BY 1 HAVING count(*) > 1) d ON d."<COL>" = t."<COL>";
```

> **禁止**「只建 `NumberSequence` 而不处理历史编号」：那样 `currentValue` 与库内既有编号不一致，新业务发号会与历史号**撞号**；且因历史列曾经可空，撞号不会立即报错，会**静默产生重号**。
> **`currentValue` 必须同步到历史最大序号之后**，而非「历史行数」—— 见下方模板（取 `max(序号段)`，**不是** `count(*)`）。

**`currentPeriod` / `currentValue` 同步模板**（对 15 个 code 逐一执行，替换 `<CODE>` / `<TABLE>` / `<COL>` / `<PERIOD_LEN>`）

```sql
-- <PERIOD_LEN>：yyyyMMdd → 3；yyyyMM → 2（split_part 的段号）
WITH cur AS (
  SELECT split_part("<COL>", '-', 2) AS period,
         max(NULLIF(regexp_replace(split_part("<COL>", '-', 3), '\D', '', 'g'), '')::int) AS max_seq
  FROM   "<TABLE>"
  WHERE  "<COL>" ~ '^[A-Z]+-[0-9]+-[0-9]+$'
  GROUP  BY 1
  ORDER  BY 1 DESC
  LIMIT  1
)
UPDATE "NumberSequence" ns
SET    "currentPeriod" = COALESCE((SELECT period  FROM cur), ''),
       "currentValue"  = COALESCE((SELECT max_seq FROM cur), 0),
       version        = version + 1
WHERE  ns.code = '<CODE>';
```

### 6.1 A. Migration Process Validation（允许引用旧表）

> **用途**：确认**旧数据是否已正确搬到新表**。本节**允许**引用旧表 / 旧字段（`SalesPipeline` / `Order` / `Quotation_deprecated` / `type` / `items`），因为它的目的就是「新 vs 旧」比对。

```sql
-- 1) 行数守恒（旧 → 新）
SELECT 'Customer',    (SELECT count(*) FROM "Customer")
UNION ALL SELECT 'Product',      (SELECT count(*) FROM "Product")
UNION ALL SELECT 'Opportunity',  (SELECT count(*) FROM "SalesPipeline")
UNION ALL SELECT 'Lead',         (SELECT count(*) FROM "Lead")
UNION ALL SELECT 'SalesOrder',   (SELECT count(*) FROM "Order" WHERE type = 'ORDER')
UNION ALL SELECT 'Quotation',
          (SELECT count(*) FROM "Order" WHERE type = 'QUOTE')
        + (SELECT count(*) FROM "Quotation_deprecated")
        - (SELECT count(*) FROM _quotation_dup)
UNION ALL SELECT 'SampleOrder',  (SELECT count(*) FROM "Order" WHERE type = 'SAMPLE')
UNION ALL SELECT 'ProductionOrder', (SELECT count(*) FROM "Order" WHERE type = 'PRODUCTION')
UNION ALL SELECT 'Shipment',     (SELECT count(*) FROM "Order" WHERE type = 'SHIPPED')
UNION ALL SELECT 'Payment',      (SELECT count(*) FROM "PaymentRecord")
UNION ALL SELECT 'Profit',       (SELECT count(*) FROM "ProfitRecord");

-- 2) 无孤儿外键（新表内部）
SELECT count(*) FROM "SalesOrderItem" i
  LEFT JOIN "SalesOrder" o ON o.id = i."orderId" WHERE o.id IS NULL;          -- 期望 0
SELECT count(*) FROM "LeadItem" i
  LEFT JOIN "Lead" l ON l.id = i."leadId" WHERE l.id IS NULL;                 -- 期望 0
SELECT count(*) FROM "Opportunity" o
  LEFT JOIN "Customer" c ON c.id = o."customerId" WHERE c.id IS NULL;         -- 期望 0
SELECT count(*) FROM "Opportunity" o
  LEFT JOIN "Lead" l ON l.id = o."leadId"
  WHERE o."leadId" IS NOT NULL AND l.id IS NULL;                              -- 期望 0（§3.3）

-- 3) 明细数量守恒（按父单比对；JSON 一律走安全函数，禁止 ::jsonb 直转）
SELECT o.id,
       jsonb_array_length(migration_try_jsonb(o.items)) AS old_cnt,
       count(i.*)                                       AS new_cnt
FROM "Order" o
LEFT JOIN "SalesOrderItem" i ON i."orderId" = o.id
WHERE o.type = 'ORDER'
  AND migration_try_jsonb(o.items) IS NOT NULL
  AND jsonb_typeof(migration_try_jsonb(o.items)) = 'array'
GROUP BY o.id HAVING count(i.*) <> jsonb_array_length(migration_try_jsonb(o.items));  -- 期望空集

-- 4) Quotation 去重一致性（旧两源 → 新单表）
SELECT (SELECT count(*) FROM "Order" WHERE type = 'QUOTE')
     + (SELECT count(*) FROM "Quotation_deprecated")
     - (SELECT count(*) FROM _quotation_dup)                     AS expected,
       (SELECT count(*) FROM "Quotation")                        AS actual;

-- 5) LeadItem 侧重映射完成度
SELECT count(*) FROM "LeadItem" i
LEFT JOIN "Lead" l ON l.id = i."leadId" WHERE l.id IS NULL;                   -- 期望 0

-- 6) 异常数据必须全部可追踪
SELECT error_type, count(*) FROM migration_error GROUP BY 1 ORDER BY 2 DESC;
SELECT count(*) FROM migration_error WHERE resolved = false;                  -- 迁移完成时必须为 0
```

### 6.2 B. Target Schema Validation（**禁止引用旧表**）

> **硬约束**：本节用于确认「**新 Schema 建成后目标库自身**是否完整、干净、可用」，因此**禁止**出现 `SalesPipeline` / `Order(type=…)` / `Quotation_deprecated` / `pipelineId` / `items` 等旧对象引用。
> 错误示例（**禁止**）：`SELECT count(*) FROM "SalesPipeline";` / `SELECT count(*) FROM "Order" WHERE type = 'ORDER';`
> 正确方向：`SELECT count(*) FROM "Opportunity";` / `SELECT count(*) FROM "SalesOrder";`

**1｜Schema 结构（表 / 字段 / FK / Unique / Index / CHECK）**

```sql
-- 1.1 目标表必须全部存在（50 张业务表 + 1 张关联表 = 51）
SELECT count(*) FROM information_schema.tables
WHERE table_schema = 'public' AND table_type = 'BASE TABLE';                  -- 期望 ≥ 51

-- 1.2 关键字段必须存在
SELECT table_name, column_name FROM information_schema.columns
WHERE (table_name, column_name) IN (
  ('Opportunity','leadId'), ('Quotation','opportunityId'), ('Quotation','customerId'),
  ('SalesOrder','opportunityId'), ('SalesOrder','quotationId'), ('SalesOrder','sampleOrderId'),
  ('ProductionOrder','salesOrderId'), ('Shipment','salesOrderId'),
  ('Payment','salesOrderId'), ('Payment','purchaseOrderId'),
  ('QualityInspection','productionOrderId'), ('QualityInspection','shipmentId'),
  ('Shipment','freightAmount'), ('Shipment','freightCurrency'), ('Shipment','freightAmountCny'),
  ('PurchaseOrderItem','productionOrderItemId')
```

### 6.3 C. Reconciliation（迁移前后数量与金额对账）

**9 个核心实体逐项对账**（旧数量 → 新数量 → 差异 → 差异原因）：

| 实体 | 旧来源 | 新目标 | 期望关系 |
|---|---|---|---|
| `Lead` | `Lead` | `Lead` | 1:1（仅补号 / 状态枚举） |
| `Customer` | `Customer` + `SalesPipeline` 补建 | `Customer` | 新 ≥ 旧（补建） |
| `Opportunity` | `SalesPipeline` | `Opportunity` | 1:1 |
| `Quotation` | `Order(type=QUOTE)` + `Quotation_deprecated` − 去重 | `Quotation` | 旧和 − 重复 = 新 |
| `SampleOrder` | `Order(type=SAMPLE)` + pipeline 补建 | `SampleOrder` | 新 ≥ `Order(type=SAMPLE)` |
| `SalesOrder` | `Order(type=ORDER)` + pipeline 补建 + B2 补建 | `SalesOrder` | 新 ≥ 旧 |
| `ProductionOrder` | `Order(type=PRODUCTION)` | `ProductionOrder` | 1:1 |
| `Shipment` | `Order(type=SHIPPED)` | `Shipment` | 1:1 |
| `Payment` | `PaymentRecord` | `Payment` | 1:1（剔除 B6 异常行时需记录） |

```sql
-- 对账模板（逐实体执行；`diff` 必须能用下方「差异原因」表解释）
WITH r AS (
  SELECT 'SalesOrder' AS entity,
         (SELECT count(*) FROM "Order" WHERE type = 'ORDER')                       AS old_cnt,
         (SELECT count(*) FROM "SalesOrder")                                       AS new_cnt,
         (SELECT COALESCE(sum("amountCNY"), 0) FROM "Order" WHERE type = 'ORDER')  AS old_amount_cny,
         (SELECT COALESCE(sum("totalAmountCny"), 0) FROM "SalesOrder")             AS new_amount_cny
  UNION ALL
  SELECT 'Payment',
         (SELECT count(*) FROM "PaymentRecord"),
         (SELECT count(*) FROM "Payment"),
         (SELECT COALESCE(sum(amount), 0) FROM "PaymentRecord"),
         (SELECT COALESCE(sum(amount), 0) FROM "Payment")
)
SELECT entity, old_cnt, new_cnt, new_cnt - old_cnt AS diff_cnt,
       old_amount_cny, new_amount_cny,
       new_amount_cny - old_amount_cny AS diff_amount
FROM r;
```

**差异原因必须逐条登记**（不允许「差异 = 0」以外的结果没有解释）：

| `errorType` | 含义 | 对账口径 |
|---|---|---|
| `MIGRATION_EXCLUDED` | 迁移排除（如已逻辑删除 / 测试数据） | 在 `migration_error` 中登记，计入「排除数」 |
| `DUPLICATE_SOURCE` | 重复数据（`Order(type=QUOTE)` 与旧 `Quotation` 合并） | 计入「去重数」，用 `_quotation_dup` 对齐 |
| `INVALID_DATA` | 无效数据（无商机 / 无客户 / 非法日期） | 计入「无效数」，新侧减少对应行数 |
| `UNMAPPED_FK` / `UNMAPPED_ENUM` | 无法映射（枚举白名单外 / FK 找不到目标） | 计入「无法映射数」 |
| `MANUAL_CONFIRM` | 人工确认（`ProductionOrder.status=COMPLETED`、`SampleRound.result=PENDING` 等保守默认） | 数据已迁入，仅需业务复核 |

> **对账闭合判据**：`new_cnt − old_cnt = 补建数 − 排除数 − 去重数 − 无效数`，且四类差异都能在 `migration_error` 中按 `errorType` 分组查到对应行数。任何**无法解释**的差异都是 P0 阻断项。

## 10. `String → enum` 两阶段迁移（新增章）

旧库大量「枚举语义」字段实际是 `String`（甚至 `Int`），值可能是中文文案或与目标枚举名不同。**不得**直接 `ALTER COLUMN ... TYPE <enum> USING col::<enum>` —— 只要存在一个未映射值，整条语句即失败。统一采用**两阶段**：

```
阶段 A（值对齐）：把旧值逐行 UPDATE 为目标枚举的**字面量名**（映射表见 §10.1~§10.5）
                 —— 本阶段必须在**独立事务**中提交
阶段 B（类型切换）：ALTER COLUMN ... TYPE <enum> USING col::<enum>
                 —— 本阶段在**独立 migration** 中执行
```

> **为什么必须分事务**：① `ALTER TYPE ... ADD VALUE` 与新值的使用**不能同事务**（`01` §1 附件迁移规则）；② 阶段 A 的 `UPDATE` 一旦与阶段 B 同事务，PG 会在同一事务的快照下看到旧值域，类型切换失败后无法定位脏行；③ 分事务后，阶段 A 的产物可直接用 `SELECT ... WHERE col NOT IN (<枚举值>)` 做回归校验。

### 10.1 `ApprovalConfig`：列改名 + 值重命名 + 类型切换（**三步**）

`01` §1 尾部映射表的落地实现。三步**顺序不可调换**：

```sql
-- Step 1) 列改名（与取值无关，可最先执行）
ALTER TABLE "ApprovalConfig" RENAME COLUMN "type" TO "bizType";

-- Step 2) 值重命名（阶段 A，独立事务）
UPDATE "ApprovalConfig" SET "bizType" = CASE "bizType"
  WHEN 'QUOTE'      THEN 'QUOTATION'
  WHEN 'SAMPLE'     THEN 'SAMPLE_ORDER'
  WHEN 'ORDER'      THEN 'SALES_ORDER'
  WHEN 'PRODUCTION' THEN 'PRODUCTION_ORDER'
  WHEN 'SHIPPED'    THEN 'SHIPMENT'
  ELSE "bizType" END;

-- Step 2.5) 校验未映射值（期望 0；非 0 则先人工决策，禁止直切）
SELECT "bizType", count(*) FROM "ApprovalConfig"
WHERE "bizType" NOT IN ('QUOTATION','SAMPLE_ORDER','SALES_ORDER','PRODUCTION_ORDER',
                        'SHIPMENT','PURCHASE_ORDER','PAYMENT','PROFIT')
GROUP BY 1;

-- Step 3) 类型切换（阶段 B，独立 migration）
ALTER TABLE "ApprovalConfig"
  ALTER COLUMN "bizType" TYPE "ApprovalBizType" USING "bizType"::"ApprovalBizType";
```

> **不得一步 `ALTER TYPE`**：旧值 `QUOTE/SAMPLE/ORDER/…` 与目标枚举名**不同名**，直接 cast 必然报 `invalid input value for enum`。
> `PURCHASE_ORDER` / `PAYMENT` / `PROFIT` 是新增值（旧库可能没有对应配置行），因此 `ApprovalBizType` 须在 Phase 1 用 `CREATE TYPE ... AS ENUM (全部 8 值)` 一次性建好，**不要靠 `ADD VALUE` 逐步补**。

### 10.4 数组 / JSON → 枚举数组

逗号串 → 枚举数组必须**先过滤非法值**（否则 `::"SupplyMode"` 报错并中断）：

```sql
-- 前置审计：找出会丢失的值
SELECT DISTINCT unnest(string_to_array("supplyModes", ',')) AS v
FROM "Product" WHERE "supplyModes" IS NOT NULL AND "supplyModes" <> '';

ALTER TABLE "Product"
  ALTER COLUMN "supplyModes" TYPE "SupplyMode"[]
  USING (CASE
    WHEN "supplyModes" IS NULL OR btrim("supplyModes") = '' THEN ARRAY[]::"SupplyMode"[]
    ELSE COALESCE((
      SELECT array_agg(x::"SupplyMode")
      FROM   unnest(string_to_array("supplyModes", ',')) AS x
      WHERE  btrim(x) IN ('DEEP_CUSTOM','LIGHT_CUSTOM','STOCK')   -- 白名单，与枚举值逐字一致
    ), ARRAY[]::"SupplyMode"[])
  END);
```

> 白名单必须与枚举值**逐字一致**；被过滤掉的原始值写入 `migration_error`（`source_id` + `raw_value`，`error_type='UNMAPPED_ENUM'`），**不得静默丢弃**。
> `Product.colors`（逗号串）是 `String[]`（非枚举），用 `string_to_array` 即可，无需白名单（§2.2）。

### 10.5 `DailyExchangeRate` 反向语义换算 + `date` 类型化（**重点**）

本表有**两件互不相关的改造**，顺序固定：① `date` 列 `String → DateTime @db.Date`（值统一取 `createdAt::date`）；② `ratePerCNY → rateToCny` 反向语义换算。

**① `date` 类型化（统一口径：`createdAt::date`）**

| | 旧 | 新 |
|---|---|---|
| 列名 | `date` | `date` |
| 类型 | `String`（格式不一：`2026-09-13` / `20260913` / 空串 均可能存在） | `DateTime @db.Date` |
| 取值 | 不可信的自由文本 | **统一 `createdAt::date`**（不解析旧字符串，规避格式歧义） |

```sql
-- 阶段 0）审计旧格式分布（Phase 0，只统计）
SELECT length("date") AS len, count(*) FROM "DailyExchangeRate" GROUP BY 1 ORDER BY 2 DESC;

-- 阶段 A）（值对齐，独立事务）：标记与 createdAt::date 不一致的行
INSERT INTO migration_error(entity_type, source_id, error_type, error_message, raw_value)
SELECT 'DailyExchangeRate', d.id, 'INVALID_DATETIME',
       '旧 date 与 createdAt::date 不一致，按 createdAt::date 归一', COALESCE(d."date", '<NULL>')
FROM   "DailyExchangeRate" d
WHERE  COALESCE(d."date", '') <> to_char(d."createdAt", 'YYYY-MM-DD');

-- 阶段 B）（类型切换，独立 migration）：由 createdAt 重建，不依赖旧字符串
ALTER TABLE "DailyExchangeRate"
  ALTER COLUMN "date" TYPE date USING ("createdAt"::date);
```

> 直接 `USING "date"::date` 会因格式不一**整批失败**；`createdAt` 是 `timestamp` 列，`::date` 恒安全，故以它为准（`04` §11 / §6 Phase 1.4）。

**② `ratePerCNY → rateToCny`（两列语义完全相反，必须逐行取倒数，绝不可仅改名）**

| | 旧 | 新 |
|---|---|---|
| 列名 | `ratePerCNY` | `rateToCny` |
| 类型 | `Float` | `Decimal(18,8)` |
| 语义 | **1 CNY = x 外币**（人民币计价倒数） | **1 外币 = x CNY**（ADR-18：`amountCny = amount × rateToCny`） |

```sql
-- Step 1) 备份 + 列改名（备份列供回归比对，验收后再删）
ALTER TABLE "DailyExchangeRate" ADD COLUMN "ratePerCNY_backup" double precision;
UPDATE "DailyExchangeRate" SET "ratePerCNY_backup" = "ratePerCNY";
ALTER TABLE "DailyExchangeRate" RENAME COLUMN "ratePerCNY" TO "rateToCny";

-- Step 2) 语义换算（阶段 A）：
--   旧值 v 的含义是「1 CNY = v 外币」，
--   故「1 外币 = 1/v CNY」→ 新值 = 1/v
UPDATE "DailyExchangeRate"
SET    "rateToCny" = 1.0 / NULLIF("rateToCny", 0)
WHERE  "rateToCny" IS NOT NULL AND "rateToCny" <> 0;

-- Step 3) 异常值处理：v = 0（除零）/ 负值 / NULL → 换算后为 NULL，必须记录
INSERT INTO migration_error(entity_type, source_id, error_type, error_message, raw_value)
SELECT 'DailyExchangeRate', d.id, 'INVALID_DATA',
       'ratePerCNY 为 0/负值/NULL，无法换算为 rateToCny，待人工补录',
       COALESCE(d."ratePerCNY_backup"::text, '<NULL>')
FROM   "DailyExchangeRate" d
WHERE  d."rateToCny" IS NULL OR d."rateToCny" <= 0;

-- Step 4) 类型与精度（阶段 B，独立 migration）
--   ⚠ SET NOT NULL 必须在 Step 3 的异常行全部人工补录（或业务确认删除）之后执行
ALTER TABLE "DailyExchangeRate"
  ALTER COLUMN "rateToCny" TYPE numeric(18,8) USING "rateToCny"::numeric;
ALTER TABLE "DailyExchangeRate" ALTER COLUMN "rateToCny" SET NOT NULL;
```

> **回归校验**：`CNY` 行应恒为 `1`（若旧库存在 `currencyCode='CNY'` 且 `ratePerCNY=1` 的行，换算后仍为 1，自洽）；USD 行的新值应在 `6~8` 区间（旧值约 `0.13~0.16`）。执行后必须抽查：
> ```sql
> SELECT "currencyCode", "ratePerCNY_backup", "rateToCny", "date"
> FROM "DailyExchangeRate" ORDER BY "date" DESC LIMIT 20;
> ```
> （`ratePerCNY_backup` 为 Step 1 改名前的备份列，供人工比对后再删。）
> **禁止**在业务代码或迁移脚本中残留 `ratePerCNY`（唯一的例外是 `ratePerCNY_backup` 备份列，且须在验收后删除），也**禁止**出现 `/ rateToCny` 的写法。

## 11. JSON / 附件 / 多态日志迁移（新增章）

### 11.1 图片 JSON → `Attachment`（含 `AttachmentOwnerType` 独立 migration）

旧库图片全部是 `String?` 里塞 JSON 数组（`images`、`certificateImages`、`ProductAudience.image` 等）。统一收敛到 `Attachment` 多态旁挂表。

**两个硬性约束**（`01` §1 / §5.2）：

1. `Attachment` **不存在反向 relation**，因此宿主 model 中**不得**声明 `images Attachment[]`（`LeadItem` 的 draft1 写法即因此被删，`03` §3.3）；
2. 每新增一个 `AttachmentOwnerType` 值，**必须使用独立 migration**，且该 migration 内**不得同时插入使用新值的业务数据**（`ALTER TYPE ... ADD VALUE` 与新值写入不能同事务）。

> **V1 无需 `ADD VALUE`**：`AttachmentOwnerType` 的 19 个值已在 Phase 1 用 `CREATE TYPE ... AS ENUM (...)` **一次性建全**，因此 V1 的图片搬迁**只有一个数据 migration**。约束 2 只约束**未来**新增宿主：届时须先发一个「只做 `ADD VALUE`」的 migration，再发数据 migration。

```sql
-- 数据搬迁（单个 migration，Phase 2.7）：
-- 对 3 个宿主逐一执行同一模板（替换 <OWNER_TYPE>；旧表名见下方 ①/②/③）
-- JSON 一律走 migration_try_jsonb（禁止 c."images"::jsonb 直接强转，见 §11.2）
INSERT INTO "Attachment"(id, "ownerType", "ownerId", name, url, "sort", "createdBy", "createdAt")
SELECT gen_random_uuid(), '<OWNER_TYPE>'::"AttachmentOwnerType", c.id,
       COALESCE(item->>'name', 'image'), item->>'url',          -- 裸串数组（SalesPipeline）改用 item #>> '{}'
       (idx - 1)::int, c."createdBy", c."createdAt"
FROM   "Customer" c                                -- ① Customer ② Product ③ Opportunity（读旧 SalesPipeline.images）
CROSS  JOIN LATERAL jsonb_array_elements(migration_try_jsonb(c."images")) WITH ORDINALITY AS t(item, idx)
WHERE  migration_try_jsonb(c."images") IS NOT NULL
  AND  jsonb_typeof(migration_try_jsonb(c."images")) = 'array';

-- 主图冗余列（Customer / Product；列表页免 join。Opportunity 无主图列）
UPDATE "Customer" c
SET    "coverImage" = migration_try_jsonb(c."images") -> 0 ->> 'url'
WHERE  migration_try_jsonb(c."images") IS NOT NULL
  AND  jsonb_typeof(migration_try_jsonb(c."images")) = 'array';

-- 非法 JSON（非 NULL / 非空串，但解析失败或非数组）→ 记异常，不阻断（§11.2）
INSERT INTO migration_error(entity_type, source_id, error_type, error_message, raw_value)
SELECT 'Attachment', h.id, 'INVALID_JSON',
       '<宿主>.images 非合法 JSON 数组，图片未迁移', left(h.raw, 500)
FROM (
  SELECT id, "images" AS raw FROM "Customer"       UNION ALL
  SELECT id, "images" FROM "Product"               UNION ALL
  SELECT id, "images" FROM "SalesPipeline"
) h
WHERE h.raw IS NOT NULL AND h.raw <> ''
  AND (migration_try_jsonb(h.raw) IS NULL OR jsonb_typeof(migration_try_jsonb(h.raw)) <> 'array');

-- 未来新增宿主的模板（独立 migration，不得含业务 INSERT）：
-- ALTER TYPE "AttachmentOwnerType" ADD VALUE IF NOT EXISTS '<NEW_HOST>';
```

**宿主 → `ownerType` 对照（19 值，值域以 `01` §1 为准）**

> **审计结论**：旧库**只有 3 个 JSON 图片数组字段**（全部为 `String?`）——`Customer.images`、`SingleProduct.images`、`SalesPipeline.images`；`Certificate.logo` 是**单个 URL 字符串**，不属数组，**不进 `Attachment`**。其余宿主（`ComboProduct` / `LeadProduct` / 各单据）**旧库根本没有图片字段**，其 `Attachment` 宿主只是**目标模型预留**，迁移时无数据可搬。

| 旧字段（全库只有这 3 个） | 元素形态 | 新 `ownerType` | 主图冗余列 |
|---|---|---|---|
| `Customer.images` | `[{url,name}]` | `CUSTOMER` | `Customer.coverImage` |
| `SingleProduct.images` | `[{url,name}]`，第 1 张为主图 | `PRODUCT` | `Product.coverImage` |
| `SalesPipeline.images` | `["url1","url2"]`（**裸字符串数组**） | `OPPORTUNITY` | — |

**目标模型预留、但旧库无数据的 `ownerType`**（19 值中余下 16 个，迁移期**不产生 `Attachment` 行**）：

`LEAD` · `LEAD_ITEM` · `OPPORTUNITY_ITEM` · `QUOTATION` · `QUOTATION_ITEM` · `SAMPLE_ORDER` · `SALES_ORDER` · `SALES_ORDER_ITEM` · `PRODUCTION_ORDER` · `QUALITY_INSPECTION` · `SHIPMENT` · `PURCHASE_ORDER` · `PAYMENT` · `COMBO_PRODUCT` · `SUPPLIER` · `CERTIFICATE`

> `LEAD_ITEM` 即 draft1 中 `LeadItem` 的 `Attachment[]` 替代方案（`03` §3.3）；V1 无对应旧数据。

> 图片 JSON 可能为 `NULL` / `''` / 非法 JSON → 逐行容错（同 §4.6），失败记 `migration_error`。
> `Customer.images` / `Product.images` 第 1 张同时写入宿主表的 `coverImage` 冗余列（列表页免 join，`01` §5.2）。

### 11.2 迁移安全函数 + 异常表 / 映射表结构（**全文件统一口径**）

**① 安全转换函数**（`migration_try_jsonb` / `migration_try_timestamp` 的唯一实现）

所有 `String → JSON / DateTime` 转换**禁止**内联 `::json` / `::jsonb` / `::timestamp`（§1.4 红线 8），统一调用下面两个函数。它们属于 **Phase 0 的迁移基础设施**（`CREATE FUNCTION`），**不进入 `schema.prisma`**：

```sql
-- 解析失败返回 NULL（而不是抛异常中断整批）
CREATE OR REPLACE FUNCTION migration_try_jsonb(txt text) RETURNS jsonb
LANGUAGE plpgsql IMMUTABLE AS $$
BEGIN
  IF txt IS NULL OR btrim(txt) = '' THEN RETURN NULL; END IF;
  RETURN txt::jsonb;
EXCEPTION WHEN others THEN RETURN NULL;
END $$;

CREATE OR REPLACE FUNCTION migration_try_timestamp(txt text) RETURNS timestamp(3)
LANGUAGE plpgsql IMMUTABLE AS $$
BEGIN
  IF txt IS NULL OR btrim(txt) = '' THEN RETURN NULL; END IF;
  RETURN txt::timestamp;
EXCEPTION WHEN others THEN RETURN NULL;
END $$;
```

> 判空在函数内部完成，调用方**不再**写 `NULLIF(x,'')`；「非空但返回 NULL」即「非法值」，由各节脚本据此登记异常。

**② `migration_error`（迁移异常表，Phase 0 建）**

```sql
CREATE TABLE IF NOT EXISTS migration_error (
  id            bigserial   PRIMARY KEY,
  entity_type   text        NOT NULL,             -- 旧实体名（Lead / Order / Quotation_deprecated / DailyExchangeRate …）
  source_id     text,                             -- 旧行 id（可空＝整表级错误）
  error_type    text        NOT NULL,             -- 受控值，见下表
  error_message text        NOT NULL,
  raw_value     text,                             -- 原始值（截断 ≤ 500 字符）
  resolved      boolean     NOT NULL DEFAULT false,
  resolved_at   timestamp(3),
  created_at    timestamp(3) NOT NULL DEFAULT now(),
  UNIQUE (entity_type, source_id, error_type)     -- 支撑 ON CONFLICT DO NOTHING（幂等，§6）
);
```

**`error_type` 受控值（全文件引用不得超出此表，禁止自造）**

| errorType | 含义 |
|---|---|
| `MISSING_REQUIRED_FK` | 目标必填外键无来源（如 `pipelineId` 为 NULL） |
| `UNMAPPED_FK` | FK 有来源但 mapping 找不到目标行 |
| `UNMAPPED_ENUM` | 枚举白名单外的值，已保守兜底 |
| `MISSING_EXCHANGE_RATE` | 非 CNY 且当日无汇率 → `exchangeRate` / `amountCny` 置 NULL（§4.7.1） |
| `DUPLICATE_SOURCE` | 两套来源合并时被丢弃的重复行（§4.2 Step 5-B） |
| `DUPLICATE_NUMBER` | 历史业务编号重复，已重新发号（§5.2） |
| `INVALID_JSON` / `EMPTY_JSON` / `NOT_ARRAY` | `items` / `images` 解析失败 / 空串 / 非数组（§4.6） |
| `INVALID_DATETIME` | `String → DateTime` 非法值，已置 NULL |
| `INVALID_DATA` | 其它非法值（`ratePerCNY=0`、负数金额等） |
| `MIGRATION_EXCLUDED` | 业务排除（逻辑删除 / 测试数据） |
| `MANUAL_CONFIRM` | 保守默认值，数据已迁入但需业务复核 |

> 与 §6.3 的「差异原因表」一一对应：`resolved=false` 的行在 **Phase 10.4** 之前必须为 0（或已人工签署豁免）。

**③ `migration_id_map`（旧 id → 新 id 映射，Phase 0 建）**

```sql
CREATE TABLE IF NOT EXISTS migration_id_map (
  entity   text NOT NULL,     -- 'SalesPipeline→Opportunity' / 'Quotation_deprecated→Quotation' / 'SalesPipeline→Lead' …
  old_id   text NOT NULL,
  new_id   text NOT NULL,
  PRIMARY KEY (entity, old_id)
);
```

> **写入一律 `ON CONFLICT (entity, old_id) DO NOTHING`**（幂等，§6）；它是 §3.3 / §3.5 / §4.2 Step 5-B 唯一的可信 ID 桥。

**④ JSON 展开的统一容错规则**

`Order.items`（§4.6）、`SingleProduct.progress`（§2.3）、各 `images`（§11.1）、`Certificate` 认证项，统一遵循：

1. `IS NULL` 或空串 → **跳过，不算错误**；
2. `migration_try_jsonb()` 返回 NULL（非空但解析失败）→ 写 `migration_error`（`entity_type` / `source_id` / `error_type` / `raw_value` 前 500 字符）；
3. 结构不是数组（物体）→ 尝试用 `jsonb_build_array()` 包装为单元素数组；仍失败则按第 2 条处理；
4. 数组元素缺 `url`/`productId` 等关键键 → 跳过该元素，**不跳过整行**。

### 11.3 `ProductActivity` → `OperationLog` / `ProductTask`；`SalesActivity` 改名

| `CustomerActivity` | `CustomerActivity` | **零 DDL**（§2.1） |


## 12. 收付款 / 利润补号与成本派生（新增章）

> **共同前提**：旧 `PaymentRecord` / `ProfitRecord` 都是 `orderId → Order`（`onDelete: Cascade`）+ `customerId`（必填），且 `paymentNo` / `profitNo` **可空、无唯一约束**。新模型把「宿主」从 `Order` 改为**具体单据表**（`SalesOrder` / `PurchaseOrder`），这是本章所有回填的基准。

### 12.1 `PaymentRecord` → `Payment`

**字段去向**

| 旧字段 | 新字段 | 规则 |
|---|---|---|
| `paymentNo String?` | `paymentNo String @unique` | 补号（`PAY`，§5）→ `SET NOT NULL` + `UNIQUE` |
| — | `direction PaymentDirection` | **新增，非空**：旧库只记录收款 → 一律 `IN` |
| `method String?`（`电汇/信用证/支付宝`） | `method String?` | **保持字符串**，不枚举化（开放取值） |
| — | `type PaymentType @default(OTHER)` | 新增：旧库无「定金/尾款/全款」语义，统一 `OTHER` |
| `orderId String`（→ `Order`） | `salesOrderId String?` | 映射见下（**不是 `pipelineId`**） |
| — | `purchaseOrderId String?` | 新增（旧库收付款不挂采购单） |
| `customerId String` | `customerId String?` | 改可空（`onDelete` 由 `Cascade` 降为 `Restrict`） |
| — | `currency` / `exchangeRate` / `amountCny` | 新增（§4.7 口径） |
| `amount Float?` | `amount Decimal(18,4)` | **改必填**；NULL 行需业务确认（置 0 并记日志，**不静默填 0**） |
| `ratio Float?` | `ratio Decimal(9,4)?` | 百分数语义，直接 cast |
| `payDate String?` | `payDate DateTime?` | `migration_try_timestamp()`（§11.2），非法置 NULL + 记 `INVALID_DATETIME` |
| `status String @default("RECEIVED")` | `status PaymentStatus @default(PENDING)` | `RECEIVED`→`RECEIVED`，`PENDING`→`PENDING`，其余→`PENDING` + 记日志 |
| `remark` / `createdBy` | 同名 | 直接 |

```sql
-- 1) 表改名 + 索引改名（见 §13，禁止 DROP + CREATE）
ALTER TABLE "PaymentRecord" RENAME TO "Payment";
ALTER INDEX "PaymentRecord_pkey" RENAME TO "Payment_pkey";
ALTER INDEX "PaymentRecord_orderId_idx"    RENAME TO "Payment_salesOrderId_idx";
ALTER INDEX "PaymentRecord_customerId_idx" RENAME TO "Payment_customerId_idx";

-- 2) 宿主回填：orderId → salesOrderId（仅当该 Order 已产出 SalesOrder）
ALTER TABLE "Payment" ADD COLUMN "salesOrderId" text;
UPDATE "Payment" p SET "salesOrderId" = so.id
FROM   "SalesOrder" so WHERE so.id = p."orderId";

-- 2.5) 无法映射的行（orderId 指向 QUOTE/SAMPLE/PRODUCTION/SHIPPED 类型）→ 阻断项 B6
INSERT INTO migration_error(entity_type, source_id, error_type, error_message, raw_value)
SELECT 'PaymentRecord', p.id, 'UNMAPPED_FK',
       'orderId=' || p."orderId" || ' 未产出 SalesOrder（B6：非 ORDER 类型宿主，须业务逐条决策）',
       p."orderId"
FROM   "Payment" p
WHERE  p."salesOrderId" IS NULL;

-- 3) 新增列
ALTER TABLE "Payment"
  ADD COLUMN "purchaseOrderId" text,
  ADD COLUMN direction "PaymentDirection" NOT NULL DEFAULT 'IN',
  ADD COLUMN type "PaymentType" NOT NULL DEFAULT 'OTHER',
  ADD COLUMN currency "Currency" NOT NULL DEFAULT 'CNY',
  ADD COLUMN "exchangeRate" numeric(18,8),
  ADD COLUMN "amountCny" numeric(18,4),
  ADD COLUMN "bankAccount" text,
  ADD COLUMN "voucherRemark" text,
  ADD COLUMN "confirmedAt" timestamp(3),
  ADD COLUMN "confirmedBy" text,
  ADD COLUMN "updatedBy" text;

-- 4) 类型切换与金额规范化（日期走安全函数，禁止 NULLIF(...)::timestamp，见 §11.2）
ALTER TABLE "Payment"
  ALTER COLUMN "amount"  TYPE numeric(18,4) USING "amount"::numeric,
  ALTER COLUMN "ratio"   TYPE numeric(9,4)  USING "ratio"::numeric,
  ALTER COLUMN "payDate" TYPE timestamp(3)  USING migration_try_timestamp("payDate"),
  ALTER COLUMN "status"  TYPE "PaymentStatus"
    USING (CASE WHEN "status" = 'RECEIVED' THEN 'RECEIVED' ELSE 'PENDING' END)::"PaymentStatus";

-- 4b) 非空但非法的 payDate → 异常表（与上一步的 NULL 结果对应）
INSERT INTO migration_error(entity_type, source_id, error_type, error_message, raw_value)
SELECT 'PaymentRecord', p.id, 'INVALID_DATETIME',
       'payDate 非法，已置 NULL，待人工补录', p."payDate"
FROM   "Payment" p
WHERE  p."payDate" IS NOT NULL AND btrim(p."payDate") <> ''
  AND  migration_try_timestamp(p."payDate") IS NULL;

-- 5) 币种 / 汇率：CNY 必须配 1；外币取宿主订单币种 + 当日汇率快照
UPDATE "Payment" p SET
  currency      = COALESCE(so.currency, 'CNY'::"Currency"),
  "exchangeRate" = CASE WHEN COALESCE(so.currency, 'CNY') = 'CNY' THEN 1 ELSE NULL END,
  "amountCny"    = CASE WHEN COALESCE(so.currency, 'CNY') = 'CNY' THEN p.amount ELSE NULL END
FROM (SELECT p2.id, so2.currency FROM "Payment" p2
      LEFT JOIN "SalesOrder" so2 ON so2.id = p2."salesOrderId") so
WHERE p.id = so.id;

-- 6) 加 CHECK（此时必须已无「双 NULL」行；新模型为「至少一个非空」）
ALTER TABLE "Payment" ADD CONSTRAINT "payment_host_ck"
  CHECK ("salesOrderId" IS NOT NULL OR "purchaseOrderId" IS NOT NULL);

-- 7) 补编号（旧列可空无唯一）
--    按 PAY 发号（§5），补号后再加约束：
ALTER TABLE "Payment" ALTER COLUMN "paymentNo" SET NOT NULL;
CREATE UNIQUE INDEX "Payment_paymentNo_key" ON "Payment"("paymentNo");
```

### 12.2 `ProfitRecord` → `Profit`（成本改为派生）

**字段去向**

| 旧字段 | 新字段 | 规则 |
|---|---|---|
| `profitNo String?` | `profitNo String @unique` | 补号（`PRF`，§5）→ `SET NOT NULL` + `UNIQUE` |
| `orderId String`（→ `Order`） | `salesOrderId String @unique` | **多对一 → 一对一**，必须先去重（见下） |
| `customerId String` | **删除** | 可由 `salesOrder.customerId` 派生（`04` §9.1） |
| `revenue Float?` | `revenue` / `revenueCny` `Decimal(18,4)` | 改必填；旧值即 CNY → `revenueCny = revenue` |
| `currency String? @default("CNY")` | `currency Currency` + `exchangeRate` | 枚举化；CNY → `exchangeRate = 1` |
| `cost Float?` | **不搬运** → 6 项成本归集（`04` §9.1 公式） | 旧手工成本无法拆分，转入 `costSnapshot.legacyCost` |
| `profit Float?` | `profitCny` | 由 `revenueCny − totalCostCny` 重算 |
| `margin Float?` | `margin Decimal(9,4) @default(0)` | 非空 + 重算 |
| — | `status` / `costSnapshot` / `calculatedAt` | 新增（`ProfitStatus @default(DRAFT)`） |
| `remark` / `createdBy` | 同名 | 直接 |

```sql
-- 1) 表改名 + 主键改名（旧 orderId 索引先保留原名，去重后再重建为唯一索引）
ALTER TABLE "ProfitRecord" RENAME TO "Profit";
ALTER INDEX "ProfitRecord_pkey" RENAME TO "Profit_pkey";

-- 2) 去重：旧 orderId 可建多条利润单，新 salesOrderId @unique → 每个 orderId 只保留 createdAt 最新一条
--    其余行先归档到 legacy 表（不删除，供业务核对）
CREATE TABLE "ProfitRecord_legacy" AS SELECT * FROM "Profit";
DELETE FROM "Profit" p USING "Profit" p2
WHERE p."orderId" = p2."orderId"
  AND (p."createdAt" < p2."createdAt" OR (p."createdAt" = p2."createdAt" AND p.id < p2.id));

-- 3) 宿主回填 + 删除冗余列
ALTER TABLE "Profit" ADD COLUMN "salesOrderId" text;
UPDATE "Profit" pf SET "salesOrderId" = so.id FROM "SalesOrder" so WHERE so.id = pf."orderId";

-- 3b) 无法映射的行 → migration_error（B6），不得静默挂到无关订单
INSERT INTO migration_error(entity_type, source_id, error_type, error_message, raw_value)
SELECT 'ProfitRecord', pf.id, 'UNMAPPED_FK',
       'orderId=' || pf."orderId" || ' 未产出 SalesOrder（B6：须业务逐条决策）', pf."orderId"
FROM   "Profit" pf WHERE pf."salesOrderId" IS NULL;

-- 3c) 唯一索引：salesOrderId 一对一生效（旧 orderId 上的普通索引不再需要）
DROP INDEX IF EXISTS "ProfitRecord_orderId_idx";
CREATE UNIQUE INDEX "Profit_salesOrderId_key" ON "Profit"("salesOrderId");
-- ⚠ SET NOT NULL 须在 3b 的未决行全部处理（改挂 / 补建 / 废弃）之后执行：
-- ALTER TABLE "Profit" ALTER COLUMN "salesOrderId" SET NOT NULL;

ALTER TABLE "Profit" DROP COLUMN "customerId";
ALTER TABLE "Profit" RENAME COLUMN "orderId" TO "legacyOrderId";   -- 保留只读备份列

-- 4) 新列 + 类型切换
ALTER TABLE "Profit"
  ADD COLUMN "revenueCny" numeric(18,4),
  ADD COLUMN currency "Currency" NOT NULL DEFAULT 'CNY',
  ADD COLUMN "exchangeRate" numeric(18,8),
  ADD COLUMN "materialCostCny"  numeric(18,4) NOT NULL DEFAULT 0,
  ADD COLUMN "outsourceCostCny" numeric(18,4) NOT NULL DEFAULT 0,
  ADD COLUMN "packagingCostCny" numeric(18,4) NOT NULL DEFAULT 0,
  ADD COLUMN "laborCostCny"     numeric(18,4) NOT NULL DEFAULT 0,
  ADD COLUMN "freightCostCny"   numeric(18,4) NOT NULL DEFAULT 0,
  ADD COLUMN "otherCostCny"     numeric(18,4) NOT NULL DEFAULT 0,
  ADD COLUMN "totalCostCny"     numeric(18,4) NOT NULL DEFAULT 0,
  ADD COLUMN "profitCny"        numeric(18,4) NOT NULL DEFAULT 0,
  ADD COLUMN margin numeric(9,4) NOT NULL DEFAULT 0,
  ADD COLUMN status "ProfitStatus" NOT NULL DEFAULT 'DRAFT',
  ADD COLUMN "costSnapshot" jsonb,
  ADD COLUMN "calculatedAt" timestamp(3),
  ADD COLUMN "updatedBy" text;

ALTER TABLE "Profit"
  ALTER COLUMN "revenue" TYPE numeric(18,4) USING COALESCE("revenue", 0)::numeric,
  ALTER COLUMN currency  TYPE "Currency"    USING COALESCE(currency, 'CNY')::"Currency";

UPDATE "Profit" SET "revenueCny" = "revenue",
  "exchangeRate" = CASE WHEN currency = 'CNY' THEN 1 ELSE NULL END;

-- 5) 成本归集（04 §9.1，R1≤4 位舍入）：从采购单 + 运费汇总，再算 total / profit / margin
UPDATE "Profit" pf SET
  "materialCostCny"  = c.material,
  "outsourceCostCny" = c.outsource,
  "packagingCostCny" = c.packaging,
  "freightCostCny"   = c.freight,
  "totalCostCny"     = c.material + c.outsource + c.packaging + c.freight
                       + pf."laborCostCny" + pf."otherCostCny",
  "profitCny"        = pf."revenueCny"
                       - (c.material + c.outsource + c.packaging + c.freight
                          + pf."laborCostCny" + pf."otherCostCny"),
  margin             = CASE WHEN pf."revenueCny" = 0 THEN 0
                            ELSE round((pf."revenueCny"
                                 - (c.material + c.outsource + c.packaging + c.freight
                                    + pf."laborCostCny" + pf."otherCostCny"))
                                 / pf."revenueCny" * 100, 4) END,
  "costSnapshot"     = jsonb_build_object(
                        'legacyCost',   (SELECT l.cost FROM "ProfitRecord_legacy" l WHERE l.id = pf."legacyOrderId"),
                        'freightKnown', false,        -- 旧库无运费来源（§4.5），freightCostCny 的 0 是「未知」而非「零运费」
                        'note', '成本按 04 §9.1 归集重算；labor/other 待人工补录；运费未知'),
  "calculatedAt"     = now()
FROM (
  SELECT pf2.id,
    COALESCE((SELECT sum(po."totalAmountCny") FROM "PurchaseOrder" po
               WHERE po."salesOrderId" = pf2."salesOrderId" AND po."purchaseType" = 'MATERIAL'), 0) AS material,
    COALESCE((SELECT sum(po."totalAmountCny") FROM "PurchaseOrder" po
               WHERE po."salesOrderId" = pf2."salesOrderId" AND po."purchaseType" = 'OUTSOURCE'), 0) AS outsource,
    COALESCE((SELECT sum(po."totalAmountCny") FROM "PurchaseOrder" po
               WHERE po."salesOrderId" = pf2."salesOrderId" AND po."purchaseType" = 'PACKAGING'), 0) AS packaging,
    COALESCE((SELECT sum(sh."freightAmountCny") FROM "Shipment" sh
               WHERE sh."salesOrderId" = pf2."salesOrderId"), 0) AS freight
  FROM "Profit" pf2
) c WHERE pf.id = c.id;
```

> **旧成本列**：`ProfitRecord_legacy`（全量快照）与 `Profit.legacyOrderId` 均为**只读备份**，待业务确认新口径一致后再清；旧 `cost` 值同时写入 `costSnapshot.legacyCost` 便于逐单复盘。
> **`laborCostCny` / `otherCostCny`** 目标为手工录入，迁移**一律置 0**，不得用旧 `cost` 填充（否则分类失真），需业务在系统上线后补录。
> **汇率缺失**：`exchangeRate` 置 NULL + 记日志。注意此处与 §4.7.1 的本金语义**不同**：`Profit` 的 6 项 `*CostCny` 是 `NOT NULL DEFAULT 0`，无法置 NULL，故只能填 0 并在 `costSnapshot` 标注「汇率缺失」；**禁止猜汇率**，也**禁止**借 0 掩盖未知来源（运费同理，见 `freightKnown`）。

### 12.3 方向 / 宿主回填顺序

```
① 表改名 + 索引改名（§13）
② 新增宿主列（可空）
③ 由 orderId 回填 salesOrderId（+ Profit 去重、删 customerId）
④ 无法映射的行 → migration_error（B6），不阻断整批
⑤ 加 CHECK 约束（此时必须已无「双 NULL」行）
⑥ 补编号（paymentNo / profitNo）→ SET NOT NULL + UNIQUE
⑦ 币种 / 汇率 / 方向 / 成本派生
```

> 顺序要点：**先回填、再去重、最后落约束**。若先加 `CHECK` / `NOT NULL` / `UNIQUE`，回填与去重过程中产生的临时非法行会被拒绝，导致整批中断。
> 新增阻断项 **B6**：`orderId` 指向非 `ORDER` 类型的行（`QUOTE`/`SAMPLE`/`PRODUCTION`/`SHIPPED`），迁移**不得**强行挂到无关的 `SalesOrder`，须业务逐条决策（补建订单 / 改挂 / 废弃）。

## 13. rename / join table 红线（新增章）

### 13.1 禁止自动 diff 的场景（共性）

Prisma Migrate 通过**名字比对**推导 `RENAME`，无法区分 `RENAME` 与「`DROP` + `CREATE`」。以下场景**必须人工编写 migration**，禁止直接 `prisma migrate dev` 自动生成：

| # | 场景 | 自动 diff 的后果 |
|---|---|---|
| 1 | 表改名（`SingleProduct` / `PaymentRecord` / `ProfitRecord` / `LeadProduct` / `SalesActivity`） | 判为 `DROP TABLE` + `CREATE TABLE` → **数据全丢** |
| 2 | 列改名（`price` / `currency` / `taxRate` / `leadNumber` / `customerCode` / `type` / `ratePerCNY` / `leader`） | 判为 `DROP COLUMN` + `ADD COLUMN` → **列数据全丢** |
| 3 | 带 `@map` 的字段改名（`ComboItem.comboId → @map("groupId")`） | 若漏写 `@map`，会误判为列改名 |
| 4 | join table 显式化（`_ProductCraftToSingleProduct`） | 会重建关联表，**关联关系全丢** |
| 5 | 枚举 `ADD VALUE` | 与数据插入同文件时会报错（§11.1） |

> **统一规则**：rename 类迁移一律写成「`ALTER TABLE ... RENAME TO` / `ALTER TABLE ... RENAME COLUMN` / `ALTER INDEX ... RENAME TO`」，**严禁 `DROP` + `CREATE`**；每个 rename 单独一个 migration 文件，并在文件头注释「人工迁移，勿自动生成」。

### 13.2 `SingleProduct` → `Product` 的两种做法（二选一）

| 做法 | DDL | 适用 |
|---|---|---|
| **A. 物理表改名**（推荐） | `ALTER TABLE "SingleProduct" RENAME TO "Product";` + 索引逐一 RENAME | 追求物理名干净、与 Prisma 默认命名一致 |
| **B. `@@map` 保留物理名** | model 名 `Product` + `@@map("SingleProduct")` | 不想动物理表；但物理名会长期与逻辑名不一致 |

> **两种做法不得混用**：若选 A，则所有 `SingleProduct_*` 索引、约束都要 RENAME；若选 B，则**不做任何表级 DDL**，但需在 `schema.prisma` 中永久保留 `@@map`，且**新索引**仍会以 `SingleProduct_` 前缀生成，命名混乱。**推荐 A**。

### 13.3 `ProductCraftLink`（join table）索引改名

旧隐式 M2M 已存在物理表 `_ProductCraftToSingleProduct`（列 `A` = 产品 id / `B` = 工艺 id）。新模型显式声明：

```prisma
model ProductCraftLink {
  productId String
  craftId   String
  product   Product      @relation(fields: [productId], references: [id], onDelete: Cascade)
  craft     ProductCraft @relation(fields: [craftId],   references: [id], onDelete: Cascade)
  @@id([productId, craftId])
  @@map("_ProductCraftToSingleProduct")
}
```

- **物理表名、`A`/`B` 列名、`_A_B_pkey` 索引名一律不变**（`A` 仍是 `SingleProduct` 的 id 值，表改名不影响外键值）；
- 若 `01`/`02` 要求把 `A`/`B` 改成 `productId`/`craftId`，则必须 `ALTER TABLE ... RENAME COLUMN "A" TO "productId"` + `ALTER INDEX "_ProductCraftToSingleProduct_AB_pkey" RENAME TO ...`，**且不得用 `@map("A")` 反向覆盖**。

> **红线**：目标 schema 中该关联表**不计入 50 张业务表**（§1.2），`model` 总数 = 51。

### 13.4 `ComboItem.groupId`：只改名、不改物

```prisma
model ComboItem {
  comboId String
  combo   ComboProduct @relation(fields: [comboId], references: [id], onDelete: Cascade)
  @@map("ComboItem")
}
```

- 逻辑名 `groupId` → `comboId`，但**物理列名保持 `groupId`**；
- 实现方式：`comboId String @map("groupId")`（**Prisma 层零 DDL**）；
- **红线**：不得写成 `ALTER TABLE "ComboItem" RENAME COLUMN "groupId" TO "comboId"`，否则与 `@map` 冲突。

### 13.5 `LeadProduct` → `LeadItem`

```sql
ALTER TABLE "LeadProduct" RENAME TO "LeadItem";
ALTER INDEX "LeadProduct_pkey" RENAME TO "LeadItem_pkey";
DROP INDEX IF EXISTS "LeadProduct_leadId_productId_key";   -- 新模型无此唯一约束
-- 外键重映射与新增列见 §3.5
```

> **红线**：`LeadProduct.leadId` 的**值语义**是 `SalesPipeline.id`，不是 `Lead.id`。只做表改名而不重映射（§3.5 Step 3），会产生**全部 `LeadItem` 挂错线索**的静默错误。

### 13.6 物理名变更总表

| 旧物理名 | 新物理名 | 方式 |
|---|---|---|
| `SingleProduct` | `Product` | `RENAME TO`（或 `@@map`，二选一，§13.2） |
| `PaymentRecord` | `Payment` | `RENAME TO` |
