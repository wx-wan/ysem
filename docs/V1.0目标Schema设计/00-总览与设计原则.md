## 1. 设计目标

### 1.1 目标主链（可追溯，但**非全链强制**）

```
Lead ──▶ Customer ──▶ Opportunity ──▶ Quotation ──▶ SampleOrder
  │                        │                              │
  │                        │  (stage 派生, 不落库)          │  最多 1 张来源
  │                        │  (outcome 显式落库)            ▼
  │                        └───────────────────▶ SalesOrder
  │                                                   │
  │                 ┌─────────────────────────────────┼──────────────────┐
  │                 ▼                                 ▼                  ▼
  │          ProductionOrder                    PurchaseOrder         Shipment
  │                 │                                 ▲                  │
  │                 │                                 │                  │
  │                 └──▶ QualityInspection ◀──────────┘                  │
  │                 │         (宿主: productionOrderId / shipmentId)      │
  │                 │                                 │                  │
  │                 └──────────────┬──────────────────┘                  │
  │                                ▼                                     │
  │                    Payment ──▶ Profit ◀───────────────────────────────┘
  │                                ▲
  └────────────────────────────────┘  (成本归集: PurchaseOrder / Shipment)
```

**可追溯链（成本归集）**

```
SalesOrderItem ──▶ ProductionOrderItem ──▶ PurchaseOrderItem ──▶ PurchaseOrder.totalAmountCny
```

| 环节 | 是否强制存在 | 说明 |
|---|---|---|
| `Lead` | ❌ 可空 | 老客户复购 / 客户直接下单时无 Lead |
| `Opportunity` | ✅ 必填（`Quotation`/`SalesOrder` 侧） | 主链锚点，必须有客户 |
| `Quotation` | ❌ 可空 | 不打样、不报价直接下单 |
| `SampleOrder` | ❌ 可空 | 多轮打样；一张 `SalesOrder` 最多 1 张来源打样单 |
| `ProductionOrder` | ❌ 可空（状态驱动） | 支持分批生产 |
| `QualityInspection` | ❌ 可空 | 宿主为生产单或出货单 |
| `Shipment` | ❌ 可空（状态驱动） | 支持分批出货 |
| `Payment` | ❌ 可空（状态驱动） | 宿主为销售订单或采购订单 |
| `Profit` | ✅ 1:1 | 计算结果快照 |

### 1.2 两条流程严格分离

| | 销售流程（Sales） | 履约流程（Fulfillment） |
|---|---|---|
| 承载对象 | Lead / Opportunity / Quotation | SalesOrder 及其下游 |
| 状态机 | `Lead.status`：`NEW → CONTACTED → QUALIFIED → CONVERTED`（支线 `INVALID`）<br>`Opportunity.outcome`：`OPEN → WON / LOST` | `DRAFT → CONFIRMED → DEPOSIT_PENDING → DEPOSIT_PAID → IN_PRODUCTION → QC → READY_TO_SHIP → SHIPPED → COMPLETED / CANCELLED` |
| 归属 | `ownerId`（业务员）+ 公海 | 订单责任人 + 生产/发货/财务各自岗位 |
| 阶段存储 | `Lead.status`（落库）+ `Opportunity.stage`（**派生，不落库**）+ `Opportunity.outcome`（**落库**） | `SalesOrder.status`（**显式落库**） |
| 驱动方式 | 人工推进 + 关键动作自动推进（生成报价 → 阶段前进） | 状态推进受**前置条件校验**约束（见 `04` 文档） |

> **Q8 决策（draft2 定案）**：`Opportunity.stage` **继续派生，不落库**。保留 `server/src/utils/pipelineStage.ts` 的派生思路，但明确其最终职责为：
> 1. **唯一职责**：根据该商机关联的下游单据（`Quotation` / `SampleOrder` / `SalesOrder` / `ProductionOrder` / `Shipment`）**计算并返回**漏斗阶段（`OPPORTUNITY → QUOTING → NEGOTIATION`），**只读、不写库**；
> 2. **不负责终态**：`WON` / `LOST` 由 `Opportunity.outcome` 表达，不由 stage 表达；
> 3. **实施阶段需同步**：`pipelineStage.ts` 的查询对象由 `prisma.order.findMany({ pipelineId })` 改为新单据表（`quotation` / `salesOrder` 等），且 `STAGE_ORDER` 的排序错误（`ORDER=6 > SHIPPED=5`）必须一并修正；
> 4. **前端**：列表/详情接口返回派生后的 `stage` 字段（只读），前端不得提交 `stage`。
>
> `stage` / `outcome` / `probability` / `intentLevel` 是**四个独立维度**，不得互相替代：
> | 维度 | 落库 | 语义 | 取值 |
> |---|---|---|---|
> | `stage` | ❌ 派生 | 漏斗推进到哪一步（客观，由单据推导） | `OPPORTUNITY` / `QUOTING` / `NEGOTIATION` |
> | `outcome` | ✅ | 商机**终态结论** | `OPEN` / `WON` / `LOST` |
> | `intentLevel` | ✅ | 客户**意向等级**（主观，人填） | `LOW` / `MEDIUM` / `HIGH` / `READY` |
> | `probability` | ✅ | **成交概率** 0~100（客观，可规则计算） | `Decimal(5,2)`，百分数语义 |

## 2. 设计原则（12 条）

| # | 原则 | 对应审计问题 |
|---|---|---|
| 1 | **一表一业务对象**。禁止用 `type` 字段在一张表里承载多种单据 | P0-1 `SalesPipeline` 四合一、P0-2 `Order` 五合一 |
| 2 | **状态机独立**。销售阶段与履约阶段不共用同一字段维度，禁止 `status`(审批态) 与 `stage`(业务态) 混用 | P0-2、P1-1 |
| 3 | **单据快照不可变**。下单/报价时把客户、产品、供应商关键字段快照进单据行；主数据后续变更不污染历史单据 | P0-3 |
| 4 | **明细必须独立表**。禁止 `items` / `progress` / `images` 用 JSON 字符串代替明细表 | P0-4、P1-6 |
| 5 | **金额双币种 + 汇率快照 + Decimal**。原币金额 + 本位币（CNY）金额 + 当时汇率三者同存，且**一律 `Decimal`**（见 §6.5） | P1-7 |
| 6 | **日期用 `DateTime`**。废弃 `String "YYYY-MM-DD"` 存业务日期；时区统一按 `Asia/Shanghai` 存 UTC | P1-8 |
| 7 | **归属统一 `ownerId`**。废止 `ownerId / assignedTo / createdBy / salesOwner` 多套命名；公海 = `ownerId IS NULL`，且**逐资源声明**哪些模块参与公海 | P1-2、P1-3 |
| 8 | **禁止级联删除业务单据**。主数据删除走软删除（`deletedAt`，**仅 4 张表白名单**）+ 停用（`status`），单据走 `CANCELLED` / `REJECTED` / `INACTIVE` | P0-5 |
| 9 | **编号统一生成**。`NumberSequence` 表统一发号，业务表只存结果编号，禁止在 controller 内散落拼接 | P2-1 |
| 10 | **附件统一存储**。`Attachment` 表按 `(ownerType, ownerId)` 旁挂；仅用于附件/日志等**旁挂对象**，不进入主业务链路 | P0-6、P2-2 |
| 11 | **禁止 `Float` 存金额/汇率/比率**。统一 `Decimal`（精度见 §6.5）；`Float` 仅允许用于尺寸、重量、体积等物理量 | P0-9（draft1 新增） |
| 12 | **重命名不得依赖 Prisma 自动 diff**。表/列重命名必须 `@@map` / `@map` 或手写 `ALTER TABLE ... RENAME` | P0-8（draft1 新增） |

> 原则 10 与「禁止多态外键」的边界：审计中批评的 `Order.targetType/targetId` 问题在于**主业务链路**用了无约束多态外键（无法 join 校验、无法级联语义）。`Attachment` 属于旁挂资源，多态是可接受且是行业惯例，但必须：① 建 `@@index([ownerType, ownerId])`；② `ownerType` 用 Prisma `enum` 收敛取值；③ 业务删除时由 service 层显式清理，不依赖数据库级联；④ **每新增一个 `ownerType` 枚举值必须使用独立 migration 文件**（详见 `01` §5.2）。

## 4. 状态机总表

### 4.1 销售侧

| 对象 | 字段 | 取值 | 终态 |
|---|---|---|---|
| `Lead` | `status` | `NEW → CONTACTED → QUALIFIED → CONVERTED`，支线 `INVALID` | `CONVERTED` / `INVALID` |
| `Opportunity` | `stage`（**派生，不落库**） | `OPPORTUNITY → QUOTING → NEGOTIATION` | 无终态（终态由 `outcome` 表达） |
| `Opportunity` | `outcome`（落库） | `OPEN → WON` / `OPEN → LOST` | `WON` / `LOST` |
| `Quotation` | `status` | `DRAFT → SUBMITTED → SENT → ACCEPTED`，支线 `REJECTED` / `EXPIRED` | `ACCEPTED` / `REJECTED` / `EXPIRED` |

**`Opportunity.outcome = WON` 判定点（Q15 定案）**

```
SalesOrder.status = CONFIRMED   ──▶   Opportunity.outcome = WON, wonAt = now()
```

| 不作为 WON 判定点的时点 | 原因 |
|---|---|
| `Quotation.status = ACCEPTED` | 客户接受报价不等于最终下单 |
| 定金到账（`DEPOSIT_PAID`） | 属于履约进度，不是销售结论 |
| 生产开始 / 出货 | 同上 |
| `Quotation.status = REJECTED` 且 30 天无新单据 | ⚠️ **不自动置 LOST**；`LOST` 仅由人工显式填写 `outcome=LOST` + `lostReason` |

**端到端销售漏斗视图**（派生 stage 的归属映射）：

| 漏斗段 | 落点 |
|---|---|
| `NEW` | `Lead.status = NEW` |
| `CONTACTED` | `Lead.status = CONTACTED` |
| `QUALIFIED` | `Lead.status = QUALIFIED` |
| `OPPORTUNITY` | `Opportunity.stage = OPPORTUNITY`（派生） |
| `QUOTING` | `Opportunity.stage = QUOTING`（派生） |
| `NEGOTIATION` | `Opportunity.stage = NEGOTIATION`（派生） |
| `WON` | `Opportunity.outcome = WON` |
| `LOST` | `Opportunity.outcome = LOST` |

### 4.2 履约侧

| 对象 | 字段 | 取值 | 终态 |
|---|---|---|---|
| `SampleOrder` | `status` | `DRAFT → DESIGNING → MOLDING → SAMPLE_SENT → FEEDBACK → APPROVED`，支线 `REJECTED` / `CANCELLED` | `APPROVED` / `REJECTED` / `CANCELLED` |
| `SalesOrder` | `status` | `DRAFT → CONFIRMED → DEPOSIT_PENDING → DEPOSIT_PAID → IN_PRODUCTION → QC → READY_TO_SHIP → SHIPPED → COMPLETED`，支线 `CANCELLED` | `COMPLETED` / `CANCELLED` |
| `ProductionOrder` | `status` | `DRAFT → SCHEDULED → IN_PRODUCTION → QC_PENDING → QC_PASSED / QC_FAILED → COMPLETED`，支线 `CANCELLED` | `COMPLETED` / `CANCELLED` |
| `QualityInspection` | `result` | `PENDING → PASSED / FAILED / CONDITIONAL` | `PASSED` / `FAILED` |
| `Shipment` | `status` | `DRAFT → BOOKED → SHIPPED → ARRIVED → COMPLETED`，支线 `CANCELLED` | `COMPLETED` / `CANCELLED` |
| `PurchaseOrder` | `status` | `DRAFT → ORDERED → PARTIAL → ARRIVED`，支线 `CANCELLED` | `ARRIVED` / `CANCELLED` |
| `Payment` | `status` | `PENDING → RECEIVED → CONFIRMED`，支线 `FAILED` | `CONFIRMED` / `FAILED` |
| `Profit` | `status` | `DRAFT → CONFIRMED` | `CONFIRMED` |

### 4.3 SalesOrder 状态推进前置条件（强制校验）

| 目标状态 | 前置条件（不满足则拒绝流转） |
|---|---|
| `CONFIRMED` | 至少 1 条 `SalesOrderItem`；客户与交期已填 → **同时触发 `Opportunity.outcome = WON`** |
| `DEPOSIT_PENDING` | `depositAmount > 0` 或 `depositRatio > 0` |
| `DEPOSIT_PAID` | 存在 `Payment(direction=IN, type=DEPOSIT, status=CONFIRMED)` 且累计 ≥ `depositAmount` |
| `IN_PRODUCTION` | 存在 ≥1 张 `ProductionOrder`（非 `CANCELLED`） |
| `QC` | 关联 `QualityInspection`（宿主为本订单的 `ProductionOrder` 或 `Shipment`）且 `result != PENDING` |
| `READY_TO_SHIP` | 最近一次 QC `PASSED` 或 `CONDITIONAL` |
| `SHIPPED` | 存在 `Shipment.status ∈ {SHIPPED, ARRIVED, COMPLETED}` |
| `COMPLETED` | `paidAmountCny >= totalAmountCny` **且** 所有 `Shipment` 已 `COMPLETED` |

> 该表把「履约阶段」从「人工点选」变为「由业务事实驱动」，是解决审计 P0-2 的核心机制。
> 注意：`QC` 前置条件中的 QC 单据**不直接挂 `SalesOrder`**，而是通过 `ProductionOrder.salesOrderId` / `Shipment.salesOrderId` 间接追溯（见 `04` §5）。

## 6. 命名 / 类型 / 审计字段规范

### 6.1 命名

| 对象 | 规范 | 示例 |
|---|---|---|
| Model | 单数 PascalCase | `SalesOrder`、`QualityInspection` |
| 字段 | 小驼峰 | `unitPrice`、`exchangeRate` |
| 编号字段 | `xxxNo`，全局 `@unique` | `orderNo`、`quotationNo`、`inspectionNo` |
| 金额 | `xxxAmount`（原币）/ `xxxAmountCny`（本位币） | `totalAmount`、`totalAmountCny` |
| 币种 | `currency`，**默认 `USD`**（报价/订单）；采购/费用默认 `CNY` | — |
| 汇率 | `exchangeRate`，语义 = `rateToCny`（1 原币 = x CNY） | — |
| 状态 | `status`；商机漏斗用派生 `stage`（不落库）；商机终态用 `outcome` | `SalesOrder.status`、`Opportunity.outcome` |
| 归属 | `ownerId`（唯一允许的归属字段名） | `Lead.ownerId` |
| 审计 | `createdBy` / `createdAt` / `updatedBy` / `updatedAt`（`deletedAt` **仅 4 张表**） | — |

### 6.2 通用审计字段片段

```prisma
  createdBy String?
  createdAt DateTime  @default(now())
  updatedBy String?
  updatedAt DateTime  @updatedAt
```

> `deletedAt DateTime?` **不属于通用片段**。V1 仅以下 4 张表声明该字段（Q9 定案）：
> `User`、`Supplier`、`Product`、`Customer`。
> 其余对象（含 `Lead` / `Opportunity` / `Quotation` / `SampleOrder` / `ComboProduct` / `Attachment`）**不得**声明 `deletedAt`。

### 6.3 通用软删除约定（Q9 定案）

| 对象类型 | 删除语义 |
|---|---|
| **软删除白名单（仅 4 张）**：`User` / `Supplier` / `Product` / `Customer` | `deletedAt != null`（+ `status = INACTIVE`），历史单据仍可引用 |
| 业务单据与业务对象（`Lead` / `Opportunity` / `Quotation` / `SampleOrder` / `SalesOrder` 及下游） | **不允许物理删除，也不软删除**，用 `status = CANCELLED` / `REJECTED` / `INACTIVE` 表达；已 `COMPLETED` 的单据不可取消 |
| 明细行（`*Item`） | 随主单物理删除（仅主单为 `DRAFT` 时允许） |
| 旁挂资源（`Attachment`） | **物理删除** + 定时孤儿清理（`ownerType/ownerId` 无宿主时回收）；不使用 `deletedAt` |
| 日志（Activity / OperationLog） | 只增不改不删 |

> **删除后的查询过滤机制在**后续代码实施阶段处理**（Prisma Client Extension / `$extends` 统一注入 `deletedAt: null`），本设计文档只记录规则。边界须知：Extension **不覆盖** `$queryRaw`、聚合与嵌套 include 的部分场景，实施时必须逐项验证。

### 6.4 外键删除行为矩阵

| 关系 | `onDelete` |
|---|---|
| 主数据 ← 单据（如 `SalesOrderItem.productId`） | `Restrict`（禁止删被引用主数据）或 `SetNull` + 快照兜底 |
| 单据 ← 明细（如 `SalesOrder → SalesOrderItem`） | `Cascade`（唯一允许级联的位置） |
| 单据 ← 单据（如 `SalesOrder → ProductionOrder`） | `Restrict` |
| `User` ← 任何业务对象 | `SetNull`（人员离职不销毁业务数据） |
| `*Activity` / `Attachment`（旁挂） | `Cascade`（`Attachment` 无 FK，靠 service 层清理） |
| `Opportunity.leadId` → `Lead` | `SetNull` |
| `SalesOrder.sampleOrderId` → `SampleOrder` | `SetNull` |

### 6.5 金额 / 汇率 / 比率类型规范（Q7 / Q13 / P1-2 定案）

**类型与精度**

| 语义 | Prisma | PostgreSQL | 说明 |
|---|---|---|---|
| 金额（原币 / 本位币） | `Decimal @db.Decimal(18, 2)` | `numeric(18,2)` | 18 位总长，2 位小数（分位） |
| 单价 | `Decimal @db.Decimal(18, 6)` | `numeric(18,6)` | 外贸单价常见 0.0001 USD 级 |
| 数量 | `Decimal @db.Decimal(18, 4)` | `numeric(18,4)` | 支持 kg / m 等非整数 |
| 汇率 | `Decimal @db.Decimal(18, 8)` | `numeric(18,8)` | JPY / KRW 折算需 8 位 |
| 比率（税率/折扣/比例/利润率/概率） | `Decimal @db.Decimal(9, 4)` | `numeric(9,4)` | **百分数语义** |

> **精度唯一来源**：本表与 `01` §1.2 严格同步（金额 `(18,2)`、单价 `(18,6)`、数量 `(18,4)`、汇率 `(18,8)`、比率 `(9,4)`），`02`~`04` 不得另立精度标准。

**禁止**：`Float`、`@db.Real`、`@db.DoublePrecision` 用于金额 / 汇率 / 比率。
**允许**：`Float` 仅用于尺寸（`sizeL/W/H`）、重量（`weight`）、体积（`volume`）等物理量。

**比率语义（Q13）**：`13.0000 = 13%`、`100.0000 = 100%`、`0.5000 = 0.5%`。
适用于 `taxRate` / `discount` / `ratio` / `margin` / `probability`；**不改为小数（0.13）**，以免与现有数据语义冲突。

**汇率语义（Q18 / P1-2）**

```
字段：rateToCny / exchangeRate   语义：1 单位目标币种 = X CNY
示例：USD → 7.2  ⇒  1 USD = 7.2 CNY
公式：amountCny = amount × exchangeRate
```

- **禁止**在正向业务逻辑中使用 `amount / exchangeRate`（反向换算仅允许出现在补数据脚本中）。
- 单据必须快照当时汇率（`exchangeRate`）；缺当日汇率时**置 NULL + 记日志**，禁止按 `1.0` 或近似值入库。
- **删除所有 `ratePerCNY` 字段与「1 CNY = x 目标币种」的反向注释。**

**计算与舍入**

```
amount         = quantity × unitPrice          （Decimal 运算，ROUND_HALF_UP 至 2 位）
amountCny      = amount × exchangeRate         （ROUND_HALF_UP 至 2 位）
totalAmount    = Σ amount
totalAmountCny = Σ amountCny
profitCny      = revenueCny − totalCostCny
margin         = revenueCny > 0 ? (profitCny / revenueCny × 100) : 0   （百分数，4 位）
```

**API 序列化（Q7 定案）**

```json
{ "amount": "1234.5600", "amountCny": "8765.4321" }
```

| 约定 | 内容 |
|---|---|
| API 输出 | 金额 / 汇率 / 比率**统一序列化为字符串**（保留数据库精度，不做 `Number()`） |
| 前端禁止 | 禁止直接依赖 JS `number` 做金额运算（`+` / `toFixed()` 会静默出错） |
| 前端计算 | 统一使用 `decimal.js` 或后端返回的计算结果 |
| 前端展示 | 统一通过金额格式化工具（按币种小数位、千分位）渲染 |
| 存储 vs 展示 | **存储精度（4/6/8 位）与展示精度（按币种 0~2 位）必须区分**，展示层不得反向影响存储精度 |
| 前端提交 | 前端提交金额一律传字符串，后端用 `new Prisma.Decimal(str)` 校验后再写库 |

> **实施提醒**：`Prisma.Decimal` 经 `res.json()` 本就输出字符串。若现有前端把金额当 `number` 使用，切换时会出现「字符串拼接」类缺陷，必须在前端改造清单中逐项排查（金额排序、求和、比较、`toFixed`、表单受控值）。

### 6.6 币种枚举（Q12 定案）

```prisma
enum Currency {
  CNY  USD  EUR  GBP  JPY  HKD
  AUD  CAD  KRW  RUB  SEK  NOK  DKK
}
```

- 共 **13 个值**，全部统一（00~05 及 `01`~`04` 的 schema 片段）。
- **本位币固定 `CNY`**（Q4 定案）。
- 报价 / 销售订单默认 `USD`；采购 / 内部费用默认 `CNY`。
- 展示小数位：`JPY` / `KRW` 为 0 位，其余 2 位（**仅影响展示，不影响存储精度**）。

| R3 | `Opportunity.probability` 是否由规则自动计算 | A. 全人工<br>B. 按 `intentLevel` 映射默认值<br>C. 按 stage 加权 | **B + C 可后续叠加**，V1 先人工 + 默认值 |
| R4 | `SalesOrder → ProductionOrder` 是否允许跨订单合并生产 | A. 不允许（1 生产单只服务 1 销售订单）<br>B. 允许（多对多） | **A**（V1 简化，`ProductionOrder.salesOrderId` 必填） |
| R5 | 历史数据补号后的 `NumberSequence` 起始值 | 见 `05` §5（按各表历史最大值 + 1，并同步 `currentPeriod`） | 见 `05` §5 |

## 8. 实施顺序建议（后续阶段执行，非本阶段）

1. **冻结期**：停止在旧 `SalesPipeline` / `Order` / `SingleProduct` 上开发新功能。
2. **建新表 / 改名**：按 `01 → 02 → 03 → 04` 顺序执行；**重命名与 join table 相关迁移必须人工设计**（见 `05` §13 红线）。
3. **数据搬迁**：执行 `05` 文档的迁移脚本（一次性，幂等，可重跑）。
4. **切换读写**：后端 controller 改为读写新表，旧表置只读。
5. **清理**：确认无引用后删除 `SalesPipeline` / `Order`。

> **红线（`05` §13）**：禁止使用 `prisma migrate dev --create-only` 自动 diff 处理业务表 rename、join table rename 或高风险 FK 迁移。这些迁移必须人工设计并使用 `@@map` / `@map` / `ALTER TABLE ... RENAME`。
